# Κεφάλαιο 07 — Δικαιώματα και Έλεγχος Πρόσβασης (DAC και MAC)

> **Διαβάστε το πριν από:** τα Μηχανήματα 1, 3, 6, 8, 9, 10, 11 (και κάθε φορά που η
> έξοδος του `ls -l` καθορίζει την επόμενη κίνησή σας).
> **Γιατί υπάρχει.** Το Κεφάλαιο 05 σας έμαθε να *καταχράστε* `sudo`, SUID και
> capabilities. Αυτό το κεφάλαιο σας μαθαίνει το σύστημα πάνω στο οποίο στηρίζονται:
> πώς το Linux αποφασίζει ποιος επιτρέπεται να κάνει τι — πρώτα το συνηθισμένο μοντέλο
> δικαιωμάτων (**DAC**), μετά τις πολιτικές που επιβάλλει ο πυρήνας και επιβιώνουν από
> έναν λογαριασμό που έχει παραβιαστεί (**MAC**: SELinux και AppArmor). Χωρίς αυτό, η
> αναβάθμιση προνομίων μοιάζει με μαγεία· με αυτό, κάθε εύρημα στα μηχανήματα έχει αιτία.

**Πλήρης ανάπτυξη:** [`docs/CONCEPTS.md`](../docs/CONCEPTS.md) §15.

---

## 1. Οι δύο ερωτήσεις που απαντά ο έλεγχος πρόσβασης

| Ερώτηση | Μοντέλο | Το επιβάλλει | Το παρακάμπτει |
| --- | --- | --- | --- |
| *Ποια είναι αυτή η διεργασία;* | **DAC** — Discretionary Access Control | τα bits `rwx` του ιδιοκτήτη | γίνεσαι root, SUID, εγγράψιμα αρχεία |
| *Ακόμη και ως root, τι επιτρέπεται να κάνει;* | **MAC** — Mandatory Access Control | ο πυρήνας (SELinux/AppArmor), πολιτική που δεν μπορείτε να αλλάξετε ως χρήστης | πολιτική *απούσα*, *permissive* ή *λάθος ρυθμισμένη* |

Το DAC είναι **διακριτικό**: ο ιδιοκτήτης του αρχείου αποφασίζει τα δικαιώματα. Το MAC
είναι **υποχρεωτικό**: μια πολιτική σε επίπεδο συστήματος αποφασίζει, και ακόμη και ο
root περιορίζεται μέχρι να ξαναφορτώσει την πολιτική. Τα περισσότερα αρχάρια μηχανήματα
χρειάζονται μόνο DAC· τη στιγμή που συναντάτε CentOS ή θωρακισμένο Ubuntu, το MAC
καθορίζει αν το exploit σας δουλέψει.

## 2. Το DAC, με ακρίβεια

### 2.1 Τα εννέα bits

```text
-rwxr-xr--  1 alice developers  4096 report.txt
 │└┬┘└┬┘└┬┘
 │ │  │  └ others: r-- (μόνο ανάγνωση)
 │ │  └ group:  r-x (ανάγνωση + εκτέλεση)
 │ └ owner:  rwx (ανάγνωση + εγγραφή + εκτέλεση)
 └ τύπος: - αρχείο, d κατάλογος, l σύνδεσμος, s socket, c/b συσκευή
```

Τρεις κατηγορίες (**ιδιοκτήτης, ομάδα, άλλοι**), τρία bits η καθεμία (**r, w, x**). Το
οκταδικό είναι απλώς η τιμή κάθε τριάδας: `r=4, w=2, x=1`, άρα `rwxr-xr--` = `754`.

| Οκταδικό | Συμβολικό | Σημασία |
| --- | --- | --- |
| `7` | `rwx` | τα πάντα |
| `6` | `rw-` | ανάγνωση + εγγραφή |
| `5` | `r-x` | ανάγνωση + εκτέλεση |
| `4` | `r--` | μόνο ανάγνωση |
| `0` | `---` | τίποτα |

### 2.2 Τι σημαίνουν τα bits σε έναν κατάλογο

Αυτό μπερδεύει διαρκώς τους αρχάριους. Σε **κατάλογο** τα bits σημαίνουν κάτι άλλο:

- `r` — μπορείτε να **δείτε** τα ονόματα (`ls`).
- `w` — μπορείτε να **δημιουργήσετε/διαγράψετε** καταχωρήσεις (γι' αυτό ένας εγγράψιμος
  κατάλογος είναι τόσο επικίνδυνος: διαγράφετε και αντικαθιστάτε αρχεία που δεν μπορείτε
  να διαβάσετε).
- `x` — μπορείτε να **εισέλθετε/διασχίσετε** τον κατάλογο (`cd`, ή πρόσβαση σε αρχείο
  μέσα του με πλήρη διαδρομή).

Το `--x` σε κατάλογο είναι η κλασική περίπτωση CTF «φτάνεις αρχείο που δεν μπορείς να
καταγράψεις».

### 2.3 `umask` — από πού προκύπτουν τα προεπιλεγμένα δικαιώματα

Τα νέα αρχεία δεν δημιουργούνται `777`· το **umask** της διεργασίας αφαιρείται από μια
βάση (`666` για αρχεία, `777` για καταλόγους):

```bash
umask          # π.χ. 0022
touch f; mkdir d
ls -l f d
```

```text
-rw-r--r-- 1 kali kali 0 f     # 666 - 022 = 644
drwxr-xr-x 2 kali kali 4096 d  # 777 - 022 = 755
```

> **Αμυντική σημείωση.** Ένα αδύναμο umask (`0000`) είναι ο τρόπος που αντίγραφα ασφαλείας
> και προσωρινά αρχεία καταλήγουν αναγνώσιμα από όλους. Ψάξτε το στα `/etc/profile`,
> `/etc/login.defs` και στο `.bashrc` ενός χρήστη.

## 3. Τα τρία ειδικά bits

| Bit | Οκταδικό | Εμφανίζεται ως | Αποτέλεσμα | Σημασία σε CTF |
| --- | --- | --- | --- | --- |
| **SUID** | `4000` | `s` στο owner-exec | εκτελείται ως ο **ιδιοκτήτης του αρχείου** | η #1 αναβάθμιση (Κεφ. 05) |
| **SGID** | `2000` | `s` στο group-exec | εκτελείται ως η **ομάδα**· σε κατάλογο, νέα αρχεία κληρονομούν την ομάδα | κοινόχρηστοι κατάλογοι· privesc ομάδας |
| **Sticky** | `1000` | `t` στο other-exec | σε κατάλογο, μόνο ο ιδιοκτήτης διαγράφει τα αρχεία του | `/tmp` |

```bash
find / -perm -4000 -type f 2>/dev/null    # SUID
find / -perm -2000 -type f 2>/dev/null    # SGID
find / -perm -1000 -type d 2>/dev/null    # sticky κατάλογοι
```

Διαβάστε το `-rwsr-xr-x`: το `s` βρίσκεται εκεί που θα ήταν το `x` του ιδιοκτήτη. Αν το
αρχείο είναι SUID αλλά **όχι** εκτελέσιμο (`-rwSr--r--`), το bit υπάρχει αλλά δεν έχει
νόημα — συνηθισμένο ψευδώς θετικό.

## 4. Πέρα από τα εννέα bits: ACLs, attributes, capabilities

Τα εννέα bits δεν μπορούν να εκφράσουν «ο χρήστης *bob* να διαβάζει, αλλά όχι η ομάδα».
Τρεις επεκτάσεις καλύπτουν το κενό — και καθεμία είναι επιφάνεια αναβάθμισης.

### 4.1 POSIX ACLs

```bash
getfacl /etc/shadow
setfacl -m u:bob:r /tmp/notes
```

Έξοδος `getfacl` που τελειώνει σε `mask::` και γραμμές ονομαστικών χρηστών σημαίνει ότι
υπάρχει ACL. Ψάξτε για ανεκτικό `mask::rwx` και για το `+` στο `ls -l` (`-rw-rw-r--+`).

### 4.2 Attributes αρχείων (`chattr`)

```bash
lsattr /etc/passwd
chattr +i /etc/passwd     # +i = immutable, ακόμη και ο root δεν γράφει
```

Το `chattr +i` είναι πραγματικός έλεγχος θωράκισης — και πραγματική παγίδα: αν
αντικαταστήσετε το `/etc/passwd` σε μηχάνημα όπου είναι immutable, η εγγραφή σας αποτυγχάνει
σιωπηλά.

### 4.3 Linux capabilities

Τα capabilities σπάζουν τη δύναμη του root σε ~40 κομμάτια. Το `getcap -r /` δείχνει
εκτελέσιμα που φέρουν ένα — π.χ. `cap_dac_read_search` (διαβάζει τα πάντα, παρακάμπτοντας
το DAC) ή `cap_setuid` (γίνεται οποιοσδήποτε χρήστης). Το Μηχάνημα 8 (`getcap`,
`cap_dac_read_search`) είναι το παράδειγμα· το Κεφάλαιο 05 §3 έχει την εκμετάλλευση.

## 5. MAC: SELinux και AppArmor

Όταν το DAC παρακαμφθεί (είστε root, ή ένα αρχείο είναι εγγράψιμο από όλους), το **MAC
είναι η τελευταία γραμμή άμυνας**. Και τα δύο συστήματα φέρνουν πολιτικές
**default-deny**: ένα πρόγραμμα κάνει μόνο ό,τι επιτρέπει το προφίλ του.

### 5.1 SELinux (Red Hat / CentOS / Fedora)

Κάθε διεργασία και αρχείο φέρει ένα **context**: `user:role:type:level`, π.χ.
`system_u:system_r:httpd_t:s0`. Οι κανόνες γράφονται με βάση τον **type** (`httpd_t`,
`user_home_t`). Τρεις καταστάσεις:

| Κατάσταση | `getenforce` | Συμπεριφορά |
| --- | --- | --- |
| **Enforcing** | `Enforcing` | οι παραβιάσεις **απορρίπτονται και καταγράφονται** |
| **Permissive** | `Permissive` | καταγράφονται αλλά **επιτρέπονται** — χρυσωρυχείο μάθησης |
| **Disabled** | `Disabled` | καθόλου MAC |

```bash
getenforce
ls -Z /var/www/html          # δείξε τα security contexts
semanage fcontext -l | grep httpd    # τι επιτρέπεται να αγγίξει ο httpd;
ausearch -m avc -ts recent   # διάβασε τις απορρίψεις (type=AVC)
```

> **Η στιγμή CTF.** Στο **FristiLeaks 1.3** (CentOS 6, SELinux enforcing), το shell που
> ανεβάσατε τρέχει σε λάθος **type** και απορρίπτεται — μέχρι να προσέξετε το context και
> να δουλέψετε μαζί του. Στο **Temple of Doom** το shell είναι `unconfined_t`, οπότε το
> SELinux δεν σας εμποδίζει καθόλου. *Ίδιο χαρακτηριστικό πυρήνα, αντίθετο αποτέλεσμα,
> καθορισμένο εξ ολοκλήρου από την πολιτική.*

### 5.2 AppArmor (Ubuntu / Debian / SUSE)

Βασίζεται σε **διαδρομές** αντί για labels: ένα προφίλ απαριθμεί τα **αρχεία** που
επιτρέπεται να αγγίξει ένα πρόγραμμα. Τα προφίλ ζουν στο `/etc/apparmor.d/`.

```bash
sudo aa-status                 # ποια προφίλ είναι φορτωμένα/enforced
cat /etc/apparmor.d/usr.sbin.apache2
sudo aa-complain /usr/sbin/apache2   # προφίλ σε "μόνο καταγραφή"
sudo aa-genprof /usr/bin/foo         # δημιουργία προφίλ παρατηρώντας το πρόγραμμα
```

Ο Apache στο Ubuntu φέρνει προφίλ AppArmor. **Αν δεν είναι σε enforce mode, ένα
παραβιασμένο `www-data` διαβάζει πολύ περισσότερο σύστημα αρχείων** — ακριβώς η αμυντική
σημείωση στα walkthroughs Photographer και Basic Pentesting.

> **Γιατί το MAC ενδιαφέρει τον αμυνόμενο.** Το DAC λέει «το αρχείο είναι αναγνώσιμο από
> όλους, άρα όποιος θέλει το διαβάζει». Το MAC λέει «ακόμη κι αν είναι, *αυτό το πρόγραμμα*
> δεν επιτρέπεται». Αυτή είναι η διαφορά μεταξύ μίας λάθος ρύθμισης και πλήρους παραβίασης.

## 7. Ασκήσεις

1. Στο Kali σας, δημιουργήστε `a.txt` και `b/`, τρέξτε `umask 0077`, ξαναδημιουργήστε τα
   και εξηγήστε κάθε χαρακτήρα της έξοδος `ls -l`.
2. Κάντε έναν κατάλογο `--x` για τους άλλους και αποδείξτε ότι μπορείτε να διαβάσετε
   γνωστό αρχείο μέσα του με πλήρη διαδρομή αλλά όχι να κάνετε `ls`.
3. Βρείτε ένα SUID εκτελέσιμο που *δεν* είναι εκμεταλλεύσιμο και εξηγήστε γιατί το bit
   είναι ακίνδυνο.
4. Σε Ubuntu VM, τρέξτε `sudo aa-status`· βρείτε ένα προφίλ που **δεν** είναι enforced και
   δηλώστε τι σημαίνει για έναν επιτιθέμενο.
5. Σε CentOS VM, βάλτε SELinux σε **Permissive**, προκαλέστε απόρριψη, διαβάστε την με
   `ausearch`, και επαναφέρετε **Enforcing**.

## 8. Ελέγξτε τον εαυτό σας

1. Στο `-rwxr-sr-x`, ποιο ειδικό bit είναι ενεργό και τι κάνει;
2. Γιατί ένας **εγγράψιμος κατάλογος** είναι επικίνδυνος ακόμη κι όταν τα αρχεία μέσα δεν
   είναι εγγράψιμα;
3. Δώστε τη διαφορά DAC και MAC σε μία πρόταση το καθένα.
4. Τι κάνει το SELinux *Permissive* που δεν κάνει το *Enforcing*, και γιατί είναι χρήσιμο
   και στον επιτιθέμενο **και** στον αμυνόμενο;
5. Πού βρίσκεται ένα capability σε σχέση με το SUID ως προς την κοκκοποίηση;

## 9. Σημειωμένες εντολές — κάθε είσοδος, κάθε έξοδος

### 9.1 `ls -l` / `ls -la`

```bash
ls -la /etc/passwd /tmp
```

```text
-rw-r--r--  1 root root   2871 May 11 09:41 /etc/passwd
drwxrwxrwt 12 root root   4096 May 11 09:41 /tmp
```

Το `t` στο `/tmp` είναι το **sticky bit**· το `+` θα σήμαινε ACL.

### 9.2 `getfacl` / `setfacl`

```bash
getfacl /tmp/shared
setfacl -m u:alice:rw /tmp/shared
getfacl /tmp/shared | grep -E 'user:|mask:'
```

Το `mask::` περιορίζει τα ενεργά δικαιώματα κάθε ονομαστικού χρήστη και της ομάδας.

### 9.3 `lsattr` / `chattr`

```bash
lsattr /etc/passwd
sudo chattr +i /etc/passwd
echo x | sudo tee -a /etc/passwd     # αποτυγχάνει: Operation not permitted
```

### 9.4 SELinux

```bash
getenforce
ls -Z /var/www/html | head
ausearch -m avc -ts recent 2>/dev/null | tail
```

Διαβάστε την έξοδο `ausearch` ως: `avc: denied { read } for pid=… comm="httpd" path="…"`.
Η μία αυτή γραμμή λέει *τι* μπλοκαρίστηκε, *ποιο πρόγραμμα* το ζήτησε και *ποιο αρχείο*
ήθελε — όλη η ιστορία μιας απόρριψης MAC.

### 9.5 AppArmor

```bash
sudo aa-status
sudo aa-complain /usr/sbin/apache2     # μόνο καταγραφή
sudo aa-enforce  /usr/sbin/apache2     # επαναφορά
```

Το `aa-status` τυπώνει τρεις μετρήσεις: **προφίλ φορτωμένα**, **σε enforce mode** και **σε
complain mode**. Ένα πρόγραμμα που λείπει από τη λίστα enforce είναι απροστάτευτο.
