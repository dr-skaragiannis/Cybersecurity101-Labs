## 1. Πού ζει η ταυτότητα: τα τέσσερα αρχεία

| Αρχείο | Περιέχει | Αναγνώσιμο από |
| --- | --- | --- |
| `/etc/passwd` | ονόματα, UID, GID, home, shell (**χωρίς κωδικούς**) | όλους |
| `/etc/shadow` | **hashes** κωδικών + γήρανση + κατάσταση κλειδώματος | μόνο root |
| `/etc/group` | όνομα ομάδας → GID → μέλη | όλους |
| `/etc/gshadow` | κωδικοί/διαχειριστές ομάδων | μόνο root |

### 1.1 `/etc/passwd` — επτά πεδία

```text
alice:x:1000:1000:Alice Doe,,,:/home/alice:/bin/bash
  │   │  │    │        │         │            └ login shell
  │   │  │    │        │         └ home directory
  │   │  │    │        └ GECOS (σχόλια)
  │   │  │    └ primary GID
  │   │  └ UID
  │   └ placeholder κωδικού ("x" = δες το /etc/shadow)
  └ username
```

**Τα εύρη UID έχουν σημασία:** `0` = root· `1–999` = λογαριασμοί συστήματος/υπηρεσιών (χωρίς
σύνδεση)· `1000+` = πραγματικοί άνθρωποι. Το `grep -E ':(1000|1001):' /etc/passwd` εμφανίζει τους
πραγματικούς χρήστες σχεδόν σε κάθε μηχάνημα.

### 1.2 `/etc/shadow` — τα πεδία που μετράνε

```text
alice:$6$Xy…:19000:0:99999:7:::
       │      │     │   │    │└ λογαριασμός ανενεργός (ημέρες, κενό = ποτέ)
       │      │     │   │    └ warn days
       │      │     │   └ max days
       │      │     └ min days
       │      └ τελευταία αλλαγή (ημέρες από 1970-01-01)
       └ hash κωδικού  ($6$ = SHA-512-crypt, $y$ = yescrypt, $2b$ = bcrypt)
```

Ένα αρχικό `!` ή `*` σημαίνει **κλειδωμένο** (αδύνατη σύνδεση με κωδικό). Γι' αυτό μερικές φορές
το `su` αρνείται ακόμη κι όταν έχετε τον σωστό κωδικό.

> **Διαβάστε το hash πριν το σπάσετε.** `$1$`=MD5-crypt, `$5$`=SHA-256-crypt, `$6$`=SHA-512-crypt,
> `$2y$`=bcrypt. Το πρόθεμα καθορίζει τη μορφή για `hashcat`/`john` **και** πόσο αργό θα είναι το
> σπάσιμο.

## 2. `su` έναντι `sudo` — διαφορετικές ερωτήσεις

| | `su` | `sudo` |
| --- | --- | --- |
| Ζητά | τον κωδικό του **χρήστη-στόχου** | τον **δικό σας** κωδικό (συνήθως) |
| Παρέχει | ολόκληρη νέα συνεδρία | μία εντολή, βάσει πολιτικής |
| Ρυθμίζεται σε | `/etc/pam.d/su` | `/etc/sudoers` (επεξεργασία με `visudo`) |
| Σημασία σε CTF | «επανάχρηση του κωδικού DB ως κωδικού OS» | «μία γραμμή `NOPASSWD` = root» |

```bash
su alice                 # γίνε alice (χρειάζεται ο κωδικός της)
sudo -i                  # διαδραστική σύνδεση root
sudo -u alice whoami     # μία εντολή ως alice
sudo -l                  # ΤΙ ΕΠΙΤΡΕΠΕΤΑΙ ΝΑ ΤΡΕΞΩ; — πάντα η πρώτη εντολή privesc
```

Ένας κανόνας `sudoers`:

```text
alice ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart apache2
```

Διαβάστε τα tokens στο Κεφάλαιο 05 §1. Ο κανόνας που μετράει: ένα πρόγραμμα που μπορεί να
εκτελέσει άλλο πρόγραμμα, χωρίς περιορισμούς ορισμάτων, είναι root shell μεταμφιεσμένο (δείτε
[GTFOBins](https://gtfobins.github.io/)).

## 3. PAM — το πλαίσιο πιστοποίησης

Το **PAM** (*Pluggable Authentication Modules*) είναι το στρώμα **ανάμεσα** στο πρόγραμμα και τη
βάση κωδικών. Τα `su`, `sudo`, `sshd`, `login`, `passwd`, `screen` — όλα ρωτούν το PAM, και το
PAM τρέχει μια στοίβα modules γι' αυτά.

### 3.1 Πώς μοιάζει η στοίβα μιας υπηρεσίας

```text
/etc/pam.d/su
#%PAM-1.0
auth       sufficient pam_rootok.so
auth       required   pam_unix.so
account    required   pam_unix.so
session    required   pam_env.so
```

Κάθε γραμμή είναι **τύπος · έλεγχος · module · args**:

| Πεδίο | Τιμές | Σημασία |
| --- | --- | --- |
| **τύπος** | `auth` | είσαι πραγματικά εσύ; |
| | `account` | επιτρέπεται τώρα αυτός ο λογαριασμός (κλειδωμένος/ληγμένος); |
| | `password` | πώς αλλάζει ένας κωδικός |
| | `session` | τι στήνεται/καταστρέφεται για τη συνεδρία |
| **έλεγχος** | `required` | πρέπει να περάσει· συνεχίζει, αποτυγχάνει στο τέλος |
| | `requisite` | πρέπει να περάσει· **αποτυγχάνει αμέσως** |
| | `sufficient` | αν περάσει, σταμάτα με επιτυχία (εκτός αν μετά αποτύχει `required`) |
| | `optional` | μετράει μόνο αν κανένα άλλο δεν αποφασίσει |
| **module** | `pam_unix.so` | ο κλασικός έλεγχος του shadow |
| | `pam_rootok.so` | πετυχαίνει αν είστε ήδη root |
| | `pam_faillock.so` / `pam_tally2.so` | μετρούν αποτυχίες, **κλειδώνουν** τον λογαριασμό |
| | `pam_pwquality.so` | πολιτική ισχύος κωδικού |
| | `pam_pwhistory.so` | θυμάται παλιούς κωδικούς |

> **Η γραμμή `sufficient pam_rootok.so` είναι γιατί ο root δεν χρειάζεται κωδικό για το `su`.**
> Και ένα λάθος `sufficient`/`optional` είναι κλασική παράκαμψη πιστοποίησης: μια στοίβα που
> «πετυχαίνει νωρίς» μπορεί να σας δεχτεί χωρίς τον έλεγχο που περιμένατε.

### 3.2 Ανάγνωση κλειδώματος

```bash
faillock --user alice          # πρόσφατες αποτυχημένες συνδέσεις
sudo pam_tally2 --user alice   # παλαιότερα συστήματα
lastb | head                   # αποτυχημένες συνδέσεις από btmp
```

Αν το `su` αποτυγχάνει με τον *σωστό* κωδικό, ελέγξτε για `!` στο `/etc/shadow` ή για κλείδωμα
`pam_faillock` — όχι για λάθος κωδικό.

### 3.3 Πού εμφανίζεται το PAM στα εργαστήρια

- **Corrosion: 1** και **Raven: 1** χρησιμοποιούν ροές `su`/`sudo` των οποίων οι αποτυχίες είναι
  αποφάσεις PAM (κλειδωμένος λογαριασμός, `pam_unix` έναντι προσαρμοσμένου module).
- **HA: Narak** και **W1R3S** αγγίζουν το `/etc/pam.d` ψάχνοντας λάθος ρυθμίσεις.
- Το γενικό μάθημα: **ο κωδικός είναι μόνο μία είσοδος της απόφασης.** Το PAM μπορεί επίσης να
  συμβουλευτεί χρονικό παράθυρο, μετρητή κλειδώματος, ομάδα, δακτυλικό αποτύπωμα ή διακομιστή
  LDAP — και οποιοδήποτε από αυτά μπορεί να είναι ο λόγος μιας άρνησης.

## 4. Πιστοποίηση SSH: κλειδιά, όχι κωδικοί

```bash
ssh-keygen -t ed25519 -C "kali"
cat ~/.ssh/id_ed25519.pub            # το ΔΗΜΟΣΙΟ κλειδί που διανέμετε
ssh-copy-id alice@target             # το προσθέτει στο authorized_keys της alice
ssh -i ~/.ssh/id_ed25519 alice@target
```

| Αρχείο στον server | Σκοπός |
| --- | --- |
| `/etc/ssh/sshd_config` | `PasswordAuthentication`, `PubkeyAuthentication`, `AllowUsers`, `PermitRootLogin` |
| `~/.ssh/authorized_keys` | δημόσια κλειδιά που επιτρέπεται να συνδεθούν **ως αυτός ο χρήστης** |
| `/etc/ssh/ssh_host_*_key` | η ταυτότητα του server (ό,τι καρφιτσώνει το `known_hosts`) |

> **Γιατί είναι διαδρομή privesc.** Αν μπορείτε να γράψετε στο `authorized_keys` **οποιουδήποτε**
> χρήστη (Κεφάλαιο 05: εγγράψιμα αρχεία), παίρνετε σταθερή σύνδεση ως αυτός **χωρίς κωδικό** —
> το κόλπο του Chill Hack. Το `authorized_keys` είναι επομένως αρχείο υψηλής αξίας για έλεγχο
> δικαιωμάτων.

## 6. Ασκήσεις

1. Λίστα των πραγματικών χρηστών (UID ≥ 1000) στο Kali σας με μία εντολή.
2. Δημιουργήστε χρήστη, κλειδώστε τον με `passwd -l`, αποδείξτε ότι το `su` αποτυγχάνει· εξηγήστε
   ποιο πεδίο του `/etc/shadow` άλλαξε.
3. Προσθέστε προσωρινό κανόνα σε `/etc/sudoers.d` για ένα binary με `NOPASSWD`, επικυρώστε με
   `visudo -c`, μετά αφαιρέστε τον.
4. Διαβάστε το `/etc/pam.d/sshd` και εντοπίστε κάθε γραμμή `auth`· δηλώστε τη σειρά εκτέλεσης.
5. Δημιουργήστε κλειδί SSH, εγκαταστήστε το δημόσιο για έναν χρήστη, συνδεθείτε χωρίς κωδικό· μετά
   βρείτε και εξηγήστε το αρχείο που το έκανε να δουλέψει.

## 7. Ελέγξτε τον εαυτό σας

1. Ποιο αρχείο κρατά το hash του κωδικού, και γιατί όχι το `/etc/passwd`;
2. Τι σημαίνουν τα `!` και `*` στην αρχή ενός hash στο `/etc/shadow`;
3. Δώστε τους τέσσερις **τύπους** PAM και τους τέσσερις **ελέγχους**.
4. Γιατί ο root δεν χρειάζεται κωδικό για το `su`, με όρους PAM;
5. Δώστε δύο λόγους που το `su` μπορεί να αποτύχει ακόμη και με τον σωστό κωδικό.

## 8. Σημειωμένες εντολές — κάθε είσοδος, κάθε έξοδος

### 8.1 `id` και `getent`

```bash
id
getent passwd alice
getent group docker sudo lxd
```

Το `getent` ρωτά τη στοίβα **NSS** — την ίδια πηγή που χρησιμοποιεί το σύστημα — άρα λύνει και
λογαριασμούς LDAP/NIS που δεν εμφανίζονται στα τοπικά αρχεία.

### 8.2 Κατάσταση `passwd`

```bash
sudo passwd -S alice
```

```text
alice P 05/11/2024 0 99999 7 -1
```

`P` = έγκυρος κωδικός, `L` = κλειδωμένος, `NP` = χωρίς κωδικό. Το πρώτο πεδίο είναι όλη η ιστορία.

### 8.3 `sudo -l` και `visudo`

```bash
sudo -l
sudo visudo -c
```

Το `visudo -c` ελέγχει τη σύνταξη. **Ποτέ μην επεξεργάζεστε απευθείας το `/etc/sudoers`** — ένα
τυπογραφικό κλειδώνει όλους έξω από το sudo. Χρησιμοποιήστε αρχείο στο `/etc/sudoers.d/`.

### 8.4 Επιθεώρηση PAM

```bash
ls /etc/pam.d/
cat /etc/pam.d/su
faillock --user "$USER"
```

### 8.5 Κλειδιά SSH

```bash
ssh-keygen -t ed25519
ls -l ~/.ssh
ssh -v alice@target 2>&1 | grep -i 'authentications that can continue'
```

Το `ssh -v` τυπώνει ακριβώς ποιες μεθόδους πιστοποίησης προσφέρει ο server και ποια πέτυχε — ο
γρηγορότερος τρόπος να αποσφαλματώσετε μια σύνδεση με κλειδί.
